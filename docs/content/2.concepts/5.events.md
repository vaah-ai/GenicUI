User actions cross three boundaries to reach the agent: the closed Shadow DOM, the WebSocket, and the MCP subscription filter. Each boundary has its own contract. This page walks a click from the user's cursor to the agent's next tool call and explains what can go wrong at each step.

## The `composed: true` decision

A GenicUI element lives inside a closed Shadow DOM. By default, CustomEvents dispatched inside a closed Shadow Root **do not** cross the boundary — they stop at the Shadow Root and never reach `document`. GenicUI's solution is the `composed: true` flag, which forces the event to cross the Shadow boundary:

::code-group
```ts [Inside the component]
// Source: registries/primevue/src/data-table.ts
this.dispatchEvent(new CustomEvent('row_selected', {
  detail: { rowId: '2' },
  bubbles: true,
  composed: true,   // ← crosses the closed Shadow DOM
}));
```

```ts [Runtime listener — outside the Shadow]
// Source: packages/client/src/runtime/event-bridge.ts
document.addEventListener('row_selected', (e) => {
  const componentId = (e.target as HTMLElement).closest('genic-data-table')?.getAttribute('component-id');
  if (!componentId) return;
  client.send({
    type: 'COMPONENT_EVENT',
    channel: componentId,
    payload: {
      componentId,
      action: e.type,
      detail: e.detail,
    },
  });
}, { capture: true });
```
::

::callout{type="warning"}
Events without `composed: true` are silently dropped. F19-AC1 enforces this — the runtime's event bridge only forwards events that successfully cross the Shadow boundary. A CommonJS-style dispatcher that forgets the flag will not produce any wire frames.
::

## End-to-end event flow

```text
┌─────────┐         ┌──────────────────┐         ┌─────────┐         ┌─────────┐
│  User   │         │ <genic-data-     │         │ Runtime │         │ Server  │
│  click  │         │  table> Shadow   │         │ event   │         │         │
└────┬────┘         └────────┬─────────┘         └────┬────┘         └────┬────┘
     │ click row #2          │                          │                   │
     │ ─────────────────────►│ PrimeVue @row-click      │                   │
     │                       │ Vue shim dispatches       │                   │
     │                       │ CustomEvent(              │                   │
     │                       │   'row_selected',         │                   │
     │                       │   { detail, composed:true } )              │
     │                       │ ─────────────────────────►                   │
     │                       │                          │ bridges to wire:   │
     │                       │                          │ COMPONENT_EVENT    │
     │                       │                          │ ──────────────────►│
     │                       │                          │                   │ validate,
     │                       │                          │                   │ route to subscribers,
     │                       │                          │                   │ forward to agent
     │                       │                          │                   │ ──► MCP __agent__
```

The five steps in detail:

1. **User clicks row** inside the Shadow DOM.
2. **PrimeVue** emits its native `@row-click` Vue event.
3. **Vue shim** (`packages/client/src/vue/`) translates it to a `CustomEvent('row_selected', { detail, composed: true })`.
4. **Runtime event bridge** catches the event at the document level (capture phase), serializes the payload, and emits a `COMPONENT_EVENT` frame on the WebSocket.
5. **Server** validates the payload against the component's event schema, routes it to subscribers, and forwards to the agent's MCP stream.

## `COMPONENT_EVENT` payload schema

`Source: .vaahagents/requirements/specs/features/feature-019-event-capture-forwarding.md`

```ts
{
  v: 1;
  channel: string;        // componentId
  type: 'COMPONENT_EVENT';
  payload: {
    componentId: string;  // mirrors channel
    action: string;       // event name (e.g. 'row_selected')
    detail: unknown;      // JSON-serializable payload from the CustomEvent
  };
  seq: number;            // monotonic per channel
}
```

The `detail` field is `unknown` at the wire level — the runtime passes whatever the Web Component dispatched. The server validates against the per-component event schema declared in the registry (`events.<name>.payloadSchema`).

## `subscribe_to_events` filtering

`Source: .vaahagents/requirements/specs/features/feature-018-subscribe-to-events-tool.md`

Subscriptions are scoped to one component plus an optional event-name filter. A subscription without `events` receives every event the component emits.

| Subscription `events` | What the agent receives |
|-----------------------|-------------------------|
| `["row_selected"]` | only `row_selected` |
| `["row_selected", "sort_change"]` | both, separately framed |
| omitted | every event the component emits |

The runtime never filters at the client — every event the bridge catches is sent on the wire, and the server applies the filter before forwarding to the agent. This keeps the client logic simple and centralizes policy server-side.

## Lifecycle: subscribe, receive, unsubscribe

```text
  Agent                              Server                          Component
    │  subscribe_to_events             │                                │
    │ ───────────────────────────────►│                                │
    │  { subscriptionId: "sub-9c2a" } │                                │
    │ ◄───────────────────────────────│                                │
    │                                  │                                │
    │                                  │     user clicks row            │
    │                                  │ ◄──────────────────────────────│
    │                                  │ validate, route                │
    │  COMPONENT_EVENT                 │                                │
    │ ◄───────────────────────────────│                                │
    │  { rowId: '2' }                  │                                │
    │                                  │                                │
    │  unsubscribe { sub-9c2a }        │                                │
    │ ───────────────────────────────►│                                │
    │                                  │ drop subscription              │
    │                                  │                                │
    │                                  │     component unmounts         │
    │                                  │ ◄──────────────────────────────│
    │  subscription.closed             │                                │
    │ ◄───────────────────────────────│  ← auto-cleanup                │
```

Three termination paths:

- **Explicit unsubscribe** — `unsubscribe` with the `subscriptionId`. Server drops the subscription; no further events flow.
- **Component unmount** — `unmount_component` or session teardown. Server emits `subscription.closed` with `reason: 'component_unmount'` and drops state.
- **Session close** — WebSocket disconnects. All subscriptions for that session die with the connection.

## Error handling

Malformed events (invalid payload, schema mismatch) are dropped, not rejected. The server logs a warning with the `componentId`, the event name, and the validation error, and increments a `drop_count` counter visible to operators.

| Symptom | Server action |
|---------|---------------|
| Event payload fails `events.<name>.payloadSchema` | Drop + log warning + increment `drop_count` |
| Event name not in component's `events[]` | Drop + log warning |
| Component not mounted | Drop silently |
| Channel queue overflow (> 500 frames) | Close socket with WS code 1013 |

::callout{type="info"}
The server never returns `-32004` for a malformed event — that's reserved for `update_component` patch failures. Event failures are silent by design: the agent should not retry a user click that the server has already dropped. See [Trust Boundary › Drop vs Reject](/concepts/trust-boundary#drop-vs-reject) for the rationale.
::

## Backpressure and rate limits

The internal event bus (F20) caps each socket's outbound queue at **500 frames**. When the queue overflows, the socket closes with WS code 1013 (try again later). The client reconnects with exponential backoff (1s, 2s, 4s, 8s, 30s cap) and replays from `Last-Event-ID`.

A per-component rate limit caps event delivery at **200 events/sec** (F19-AC3). Beyond that, the server drops excess events and increments `drop_count`. Components generating > 200 events/sec (autocomplete dropdowns, drag-tracked sliders) should debounce at the source rather than rely on server throttling.
