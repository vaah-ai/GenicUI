GenicUI assumes the agent is authenticated but **not trusted**. A valid API key only proves the agent has credentials — it doesn't prove the agent is benevolent. The trust boundary is the input validation pipeline that runs on every tool call before any state mutates. This page is the security reference: where the boundary sits, what it checks, and how it fails.

## Three trust zones

GenicUI has three independent trust boundaries. A breach in one does not auto-breach the next.

```text
┌─────────────────────────────────────────────────────────────┐
│  Zone 1 — Network → Server                                  │
│  • TLS termination (Cloudflare / host)                      │
│  • API key validation                                       │
│  • WebSocket subprotocol check                               │
│  Threat: unauthenticated abuse                              │
└─────────────────────────────────────────────────────────────┘
                            ↓ trusted (authenticated) ↓
┌─────────────────────────────────────────────────────────────┐
│  Zone 2 — Agent tool call → Server handler                  │
│  • JSON Schema validation (TypeBox Value.Check)            │
│  • Prototype pollution strip                                │
│  • Schema version drift detection                           │
│  • Idempotency key check                                    │
│  Threat: authenticated abuse (agent exceeding authority)    │
└─────────────────────────────────────────────────────────────┐
                            ↓ trusted (validated) ↓
┌─────────────────────────────────────────────────────────────┐
│  Zone 3 — User event → Agent                                │
│  • CustomEvent comes from Shadow DOM (less surface)         │
│  • Server-side schema check on payload                      │
│  • Agent must re-validate detail payload                    │
│  Threat: user-injected prompt manipulation                  │
└─────────────────────────────────────────────────────────────┘
```

Zone 1 is the standard network edge — Cloudflare Workers or a reverse proxy. Zone 2 is where the rest of this page focuses. Zone 3 is documented under [Events › Error handling](/concepts/events#error-handling).

## Why three zones

Each zone defends against a different adversary. A single boundary would conflate them:

- Zone 1 stops **unauthenticated** attackers from reaching the agent logic.
- Zone 2 stops **authenticated agents** from doing more than their schema permits — even if Zone 1 trusted them.
- Zone 3 stops **end users** from injecting values that manipulate the agent's next turn.

Separating them means an attacker who breaches Zone 1 still cannot trigger an unschema'd state mutation, and an attacker who breaches Zone 2 still cannot inject events through a user's browser.

## The input validation pipeline

Every inbound tool call runs through five sequential steps. Each step must pass before the next runs.

```text
Raw payload
     │
     ▼
[1] stripProtoKeys()   ──── drop __proto__, constructor, prototype recursively
     │
     ▼
[2] Value.Check()      ──── TypeBox JSON Schema validation
     │
     ▼
[3] Discriminated union ──── update_component: patch XOR merge (not both)
     │
     ▼
[4] Version drift       ──── reject drift > 2 minor versions
     │
     ▼
[5] Idempotency dedupe  ──── 24h LRU keyed by (apiKey, clientRequestId)
     │
     ▼
Tool handler (trusted)
```

| Step | Defends against |
|------|------------------|
| 1 | Prototype pollution (CVE-2018-3721, CVE-2019-7609) |
| 2 | Type confusion, missing fields, extra fields |
| 3 | Conflicting update mechanisms |
| 4 | Breaking changes the agent doesn't know about |
| 5 | Replay attacks |

The steps run in order and any failure short-circuits the rest. A failure on step 2 never reaches step 5 — no idempotency cache pollution from invalid payloads.

## `stripProtoKeys` — the prototype-pollution defense

`Source: packages/server/src/mcp/strip-proto-keys.ts`. Step 1 walks the payload recursively and drops any key named `__proto__`, `constructor`, or `prototype`:

```ts
function stripProtoKeys<T>(obj: T): T {
  if (obj === null || typeof obj !== 'object') return obj;
  if (Array.isArray(obj)) return obj.map(stripProtoKeys) as any;
  const out: any = {};
  for (const [k, v] of Object.entries(obj)) {
    if (k === '__proto__' || k === 'constructor' || k === 'prototype') continue;
    out[k] = stripProtoKeys(v);
  }
  return out;
}
```

The attack vector it blocks:

```json
// Attacker payload
{
  "props": {
    "rows": [],
    "__proto__": { "isAdmin": true }
  }
}
```

If passed to `Object.assign(target, payload)`, the prototype of `target` would gain `isAdmin: true`, affecting every other `target` instance. `stripProtoKeys` removes the malicious key before any merge happens.

::callout{type="warning"}
This is GenicUI's most-tested attack vector. F14-AC1 runs a fast-check property test with **10,000 random payloads** containing malicious keys at random depths. Every payload must come out with the dangerous keys absent. The test fails CI if any payload survives.
::

## `additionalProperties: false` enforcement

Two enforcement points, two failure modes.

### Per-tool `inputSchema` — strict at request time

Every MCP tool's `inputSchema` is emitted with `additionalProperties: false` at the wire level. TypeBox's `Value.Check()` rejects any extra field:

```ts
const schema = Type.Object({
  name: Type.String(),
  props: Type.Object({ rows: Type.Array(Type.Any()) }),
}, { additionalProperties: false });

const errors = Value.Errors(schema, payload);
if (errors.length > 0) {
  return { code: -32003, message: 'props_invalid', data: { details: errors.map(e => `${e.path}: ${e.message}`) } };
}
```

### Per-registry `propsSchema` — strict at load time

Registry authors cannot sneak in open schemas. At registry load time, the server walks the schema tree and rejects `additionalProperties: true`:

```ts
function rejectOpenSchemas(schema: TSchema): void {
  if (schema.type === 'object' && schema.additionalProperties === true) {
    throw new RegistryValidationError('additionalProperties: true is forbidden');
  }
  // recurse into properties, items, etc.
}
```

A registry with even one open schema fails to load. The server boots into a "registry invalid" state and refuses to serve any tool calls.

## Drop vs reject

The pipeline distinguishes **drop** (silent discard, log warning) from **reject** (return JSON-RPC error to the agent):

| Failure | Action | Visible to agent? |
|---------|--------|--------------------|
| `__proto__` strip | Drop + log warn | No — payload is sanitized transparently |
| TypeBox validation fail | **Reject** with `-32003 props_invalid` | Yes — agent sees the error |
| Discriminated union fail | **Reject** with `-32003 props_invalid` | Yes |
| Version drift > 2 minor | **Reject** with `-32009 version_drift` | Yes |
| Idempotency conflict | **Reject** with `-32007 idempotency_conflict` | Yes |
| Schema parse at registry load | **Reject** boot | Yes — server fails to start |
| Open schema at registry load | **Reject** boot | Yes |

The reasoning: agents need to **know** when their input is wrong so they can fix it. They don't need to know when a malicious payload was sanitized — that's the server's job, not theirs.

The Testable MVP has been exercised against the standard OWASP attack catalog. Results:

| Attack vector | Result | Test |
|---------------|--------|------|
| `__proto__` injection via tool call | **Blocked** — stripped at step 1 | `tests/integration/trust-boundary.test.ts:F14-AC1` (10K random payloads) |
| `constructor.prototype` chain | **Blocked** — stripped at step 1 | Same property test |

## Threat mitigations matrix (excerpt)

| Threat | Mitigation | Status |
|--------|-----------|--------|
| Network sniffing | TLS termination | Host responsibility |
| API key brute force | 128-bit entropy + rate limits | MVP partial (Phase 2 enforced) |
| Replay attack | TLS + WS upgrade auth | MVP |
| Prototype pollution | `stripProtoKeys` + `Object.create(null)` + frozen objects | MVP |
| Schema bypass | TypeBox + `additionalProperties: false` | MVP |
| Type confusion | TypeBox + runtime discriminated union | MVP |
| XSS in event detail | `composed: true` events JSON-serialized; agent re-validates | MVP |
| Registry supply chain | npm `--provenance` + conformance tests + manual review | MVP partial |
| Denial of service | WS heartbeat + max connections per key | MVP partial |
| User input → agent prompt | Agent must re-validate every event payload | Out of MVP scope |

The full matrix covers 15 threats. The ones deferred to Phase 2 are explicitly tagged — these are *deliberate* gaps, not oversights.
