A *provider* in GenicUI is the chat-side bridge between the playground and a local LLM CLI. Pick Claude Code, fill in its binary path, type a prompt — and the server spawns `claude` with `--output-format stream-json` and pipes the assistant's reply back as `chat.event` frames on the `__chat__` channel. This page is the protocol reference for that bridge.

## What is a Provider?

Two systems live in the chat path:

- **Client-side provider registry** — `examples/playground/app/providers/`. A static list of `ProviderDescriptor`s. Each entry declares a `configFields[]` schema (e.g. CLI binary path). The playground renders the dropdown and persists the user's selection to `localStorage`. The selected provider's config is serialized into a `ProviderWirePayload` and sent with every `chat.message` frame.
- **Server-side provider adapter** — `packages/server/src/chat/providers/`. A `ProviderAdaptor` knows how to spawn one specific LLM CLI (its argv, its binary resolution, its stdout parsing). The chat handler reads `provider.id` from the incoming frame and routes to the matching adapter.

The two systems meet at the wire: the client puts `{ id, config }` in the frame payload; the server's `getProviderAdaptor(id)` looks up the adapter that consumes `config`.

::callout{type="info"}
**Not to be confused with `@genicui/agent-bridge` providers.** That package is *server-side* HTTPS LLM clients — it never spawns a subprocess and never sees the `__chat__` channel. See [API Reference › Agent Bridge](/api/agent-bridge) for the bridge side.
::

## End-to-end connection flow

The full bridge — from a user opening the dropdown to a streamed `chat.event` landing in the chat panel:

```text
Playground (Vue)                          Server                              Local CLI
─────────────────                          ────────                           ─────────
mount → load PROVIDERS from registry.ts:
   • claude-code (enabled, cliPath)
   • codex (disabled, coming soon)
                │
                ▼  user picks Claude Code, fills CLI path
useProviders.setConfigField → persist to
  localStorage['genicui-playground:providers:v2']
                │
                ▼  user types prompt + clicks send
WebSocket frame on __chat__:
  { v: 1, channel: '__chat__', type: 'chat.message',
    payload: { prompt, registry,
               provider: { id: 'claude-code', config: { cliPath } } },
    seq: 0 }
                │                          │
                ▼                          │
  chat handler reads provider.id,          │
  calls getProviderAdaptor('claude-code')  │
                │                          │
                ▼                          │
  ClaudeCodeAdaptor.resolveBinary(config)  │
    → '/opt/homebrew/bin/claude'           │
  ClaudeCodeAdaptor.buildArgs({ resumeId })│
    → ['--print', '--output-format',       │
       'stream-json', '--verbose', ...]    │
                │                          ▼
                │                Bun.spawn(binary, args)
                │                          │
                │                CLI reads .mcp.json, discovers
                │                the GenicUI MCP server, gets 4 tools:
                │                  find_ui_component, render_component,
                │                  update_component, subscribe_to_events
                │                          │
                │                stdout stream-json →
                │                claude-code.ts::parseLine + mapStreamJsonEvent
                │                          │
                │                          ▼ ChatEvent
                ◄────────────────────────
WebSocket frame on __chat__:
  { v: 1, channel: '__chat__', type: 'chat.event',
    payload: { event: { type: 'ai_text', data: { text: '...' } } },
    seq: 7 }
                │
                ▼
useChat.handleEvent(frame) → switch (evt.type) → render in ChatPanel
```

The key insight: **the same `__chat__` channel** carries both `chat.message` (client → server, the prompt + provider) and `chat.event` (server → client, the streamed response). The `provider` field on `chat.message` is the routing key — without it, the server has no way to know which CLI to spawn.

## The two halves of a provider

| Layer | Location | Knows about |
|-------|----------|-------------|
| Client registry | `examples/playground/app/providers/` | UI rendering, `localStorage` persistence, `ProviderWirePayload` assembly |
| Server adapter | `packages/server/src/chat/providers/` | CLI binary resolution, argv construction, stdout → `ChatEvent` translation |

The two sides are intentionally decoupled — the UI scaffold can land first and the server adapter can ship later.

## `ProviderDescriptor` interface

```ts
// Source: examples/playground/app/providers/types.ts
export interface ProviderDescriptor {
  /** Stable id used in the wire payload (provider.id) and on the server. */
  id: string;
  /** Visible option label in the Providers dropdown. */
  label: string;
  /** Short description shown below the dropdown or as a tooltip. */
  description: string;
  /** Config fields rendered when this provider is selected. */
  configFields: ProviderConfigField[];
  /** If true, the provider is shown but cannot be selected yet. */
  disabled?: boolean;
}
```

Disabled entries render with the HTML `disabled` attribute — the user sees the option but cannot pick it.

## `ProviderConfigField` types

```ts
export type ProviderConfigFieldType = 'text' | 'path';

export interface ProviderConfigField {
  /** Key under `provider.config[key]` on the wire. */
  key: string;
  /** Visible label above the input. */
  label: string;
  /** Render hint — currently only `text` and `path` are implemented. */
  type: ProviderConfigFieldType;
  /** Default value when none is stored. */
  default: string;
  /** Placeholder shown inside the empty input. */
  placeholder: string;
  /** Optional helper text below the input. */
  help?: string;
}
```

`type: 'path'` is functionally identical to `'text'` today, reserved for a future path-picker UI.

## `ProviderWirePayload` wire shape

The provider block carried on every `chat.message` frame:

```ts
export interface ProviderWirePayload {
  id: string;
  /** Free-form config keyed by ProviderConfigField.key. */
  config: Record<string, string>;
}
```

What arrives on the WebSocket:

```ts
{
  v: 1, channel: '__chat__', type: 'chat.message',
  payload: {
    prompt: 'Show me San Francisco weather',
    registry: 'primevue',
    provider: { id: 'claude-code', config: { cliPath: '/opt/homebrew/bin/claude' } },
  },
  seq: 0
}
```

The server's chat handler unpacks `payload.provider.id` and calls `getProviderAdaptor(id)`. The `config` is forwarded to the adapter's `resolveBinary(config)` and `buildArgs({ resumeId })`. The adapter's `id` and `label` are server-side metadata, never sent on the wire.

## How the playground selects + persists providers

The `useProviders` composable ([`examples/playground/app/composables/useProviders.ts`](https://github.com/your-org/genicui)) is a singleton — module-level `ref`s shared across every consumer. State persists to:

```text
localStorage key:  genicui-playground:providers:v2
value (JSON):      { selectedProviderId: string, config: Record<string, Record<string, string>> }
```

The `:v2` suffix lets the playground evolve the persisted shape without colliding with the legacy key. Hydration is idempotent; corrupted JSON is swallowed leaving defaults in place. A deep `watch` persists every change after the first hydration so the initial mount doesn't overwrite persisted state with defaults.

`getWirePayload()` is the assembly point — merges persisted values over field defaults:

```ts
function getWirePayload(): ProviderWirePayload {
  return { id: selectedProviderId.value, config: getConfig() };
}
```

## How the server spawns the CLI

The server-side adapter (`packages/server/src/chat/providers/claude-code.ts`) is the only place that knows how to spawn the CLI. The flow:

```text
1. Chat handler receives chat.message, unpacks payload.provider → { id, config }
2. Calls getProviderAdaptor(provider.id) → ClaudeCodeAdaptor (or null)
3. adaptor.resolveBinary(config) → '/opt/homebrew/bin/claude'
   (priority: config.cliPath → $GENICUI_CLAUDE_BIN → 'claude' on $PATH)
4. adaptor.buildArgs({ resumeId }) → ['--print', '--output-format', 'stream-json', ...]
5. Bun.spawn(binary, args) — handler owns the lifecycle
6. Each stdout line → adaptor.parseLine(line) → ChatEvent
7. Chat handler wraps ChatEvent in a chat.event frame on __chat__
```

`resolveBinary`, `buildArgs`, and `parseLine` are pure functions — the whole adapter is testable without spawning a real process. The chat handler owns `Bun.spawn` (PID, stdout streaming, stderr buffering, exit handling) so cross-cutting concerns live in one place. `--mcp-config` tells the CLI where to find the GenicUI MCP server (default: `<repo>/.mcp.json`); `--resume <sessionId>` is passed on subsequent turns.

::callout{type="info"}
**Adapters return argv; the chat handler owns the spawn.** This split keeps each adapter trivial to unit-test and centralizes process lifecycle in one place.

## How to add a third provider (Codex as the worked example)

The server-side stub (`packages/server/src/chat/providers/codex.ts`) already exists; what remains is the real implementation plus the client-side UI to enable it.

### 1. Flip the client entry to enabled

Edit `examples/playground/app/providers/registry.ts` — flip `disabled: true` to `disabled: false` and add the `configFields` entry mirroring Claude Code's `cliPath` field (just point at the codex binary).

### 2. Implement the server-side adapter

Edit `packages/server/src/chat/providers/codex.ts` to replace the three stub methods. Shape mirrors `claude-code.ts`:

```ts
export class CodexAdaptor implements ProviderAdaptor {
  public readonly id = 'codex';
  public readonly label = 'Codex';
  resolveBinary(config: ProviderConfig): string {
    return config['cliPath']?.trim() || process.env['GENICUI_CODEX_BIN'] || 'codex';
  }
  buildArgs(opts: { readonly resumeId: string | null }): string[] {
    const args: string[] = [/* codex's equivalent flags */];
    if (opts.resumeId) args.push('--resume', opts.resumeId);
    return args;
  }
  parseLine(line: string): ParsedLine {
    // Translate codex's stdout shape into ChatEvent.
    // MUST emit one of the 7 chat.event.type values — see /concepts/chat-events.
  }
}
```

The server registry (`packages/server/src/chat/providers/registry.ts`) already maps `'codex'` → `CodexAdaptor`.

::callout{type="warning"}
**`parseLine` output MUST be one of the 7 `chat.event.type` values.** Every line that becomes a wire frame has to be `ai_text`, `tool_call`, `tool_result`, `status`, `error`, `stderr`, or `user_event` — clients drop unknown types. See [Chat events](/concepts/chat-events).
::
