A *provider* in GenicUI is the chat-side bridge between the playground and a local LLM CLI. Pick Claude Code, fill in its binary path, type a prompt — and the server spawns `claude` with `--output-format stream-json` and pipes the assistant's reply back as `chat.event` frames on the `__chat__` channel. This page is the protocol reference for that bridge.

## What is a Provider?

Two systems live in the chat path:

- **Client-side provider registry** — `examples/playground/app/providers/`. A static list of `ProviderDescriptor`s. The playground renders the dropdown and persists the user's selection to `localStorage`. The selected provider's config is serialized into a `ProviderWirePayload` and sent with every `chat.message` frame.
- **Server-side provider adapter** — `packages/server/src/chat/providers/`. A `ProviderAdaptor` knows how to spawn one specific LLM CLI (argv, binary resolution, stdout parsing). The chat handler reads `provider.id` from the incoming frame and routes to the matching adapter.

The two systems meet at the wire: the client puts `{ id, config }` in the frame payload; the server's `getProviderAdaptor(id)` looks up the adapter that consumes `config`.

::callout{type="info"}
**Not to be confused with `@genicui/agent-bridge` providers.** That package is *server-side* HTTPS LLM clients — it never spawns a subprocess and never sees the `__chat__` channel. See [API Reference › Agent Bridge](/api/agent-bridge) for the bridge side.
::

## End-to-end connection flow

::steps{level="4"}

#### 1 · Playground loads the registry

On mount, `app/providers/registry.ts` exposes the two `ProviderDescriptor`s — `claude-code` (enabled, `cliPath`) and `codex` (disabled stub). The dropdown reads from this list; nothing is fetched.

#### 2 · User picks Claude Code and fills the CLI path

`useProviders.setConfigField()` writes to `localStorage['genicui-playground:providers:v2']` as `{ selectedProviderId, config: Record<providerId, Record<key, value>> }`. Hydration is idempotent on every page load.

#### 3 · User types a prompt and clicks send

The chat input emits a `chat.message` frame on `__chat__` with `payload.provider` attached:

```ts
{
  v: 1, channel: '__chat__', type: 'chat.message',
  payload: {
    prompt: 'Show me San Francisco weather',
    registry: 'primevue',
    provider: { id: 'claude-code', config: { cliPath: '/opt/homebrew/bin/claude' } },
  },
  seq: 0,
}
```

#### 4 · Server reads `provider.id` and looks up the adapter

`packages/server/src/chat/handler.ts` unpacks `payload.provider` and calls `getProviderAdaptor(id)`, which returns the registered `ClaudeCodeAdaptor` instance.

::callout{type="info"}
**Workspace plugins use a workspace-scoped lookup.** When the playground chat-panel routes a `provider.id` matching a workspace plugin, the resolved adapter comes from the workspace's own `examples/<workspace>/server/providers/registry.ts`, not from `packages/server/src/chat/providers/registry.ts`. The framework's `getProviderAdaptor(id)` signature is unchanged; the workspace-resident `registerProvider` populates the lookup map at workspace boot. See [§ Authoring a workspace plugin](#authoring-a-workspace-plugin) for the full pattern.
::

#### 5 · Adapter resolves the binary and builds argv
`resolveBinary(config)` checks `config.cliPath` → `$GENICUI_CLAUDE_BIN` → `'claude'` on `$PATH`. `buildArgs({ resumeId })` returns `['--print', '--output-format', 'stream-json', '--verbose', ...]`. Both are pure functions; the chat handler owns `Bun.spawn(binary, args)`.

#### 6 · Spawned CLI discovers GenicUI MCP tools

The `claude` subprocess reads `.mcp.json`, registers the GenicUI MCP server, and discovers the 4 tools: `find_ui_component`, `render_component`, `update_component`, `subscribe_to_events`.

#### 7 · CLI stdout lines → `parseLine` → `ChatEvent`

Each `stream-json` line flows through `ClaudeCodeAdaptor::parseLine` and `mapStreamJsonEvent`, producing one of the 7 `chat.event.type` values — see [Chat events](/concepts/chat-events).

#### 8 · Server wraps each event in a frame on `__chat__`

```ts
{ v: 1, channel: '__chat__', type: 'chat.event',
  payload: { event: { type: 'ai_text', data: { text: '...' } } }, seq: 7 }
```

#### 9 · Playground's `useChat.handleEvent` dispatches

`switch (evt.type)` routes to the right renderer in `ChatPanel.vue` — `ai_text` appends prose, `tool_call` opens an accordion, `user_event` synthesizes a click bubble, etc.

::

The key insight: **the same `__chat__` channel** carries both `chat.message` (client → server, the prompt + provider) and `chat.event` (server → client, the streamed response). The `provider` field on `chat.message` is the routing key — without it, the server has no way to know which CLI to spawn.

## The two halves of a provider

| Layer | Location | Knows about |
|-------|----------|-------------|
| Client registry | `examples/<workspace>/app/providers/` | UI rendering, `localStorage` persistence, `ProviderWirePayload` assembly |
| Server adapter (built-in) | `packages/server/src/chat/providers/` | First-party CLI binary resolution, argv construction, stdout → `ChatEvent` translation (Claude Code, codex stub) |
| Server adapter (workspace plugin) | `examples/<workspace>/server/providers/` | Third-party HTTP APIs as agent-callable tools, fixture-mode dispatch, bearer-scrub closure (see §7 worked example) |

The two sides are intentionally decoupled — the UI scaffold can land first and the server adapter can ship later. **Built-in** server adapters (`claude-code`, `codex`) live in `packages/server/src/chat/providers/` because they are tolerable first-party entries (small, env-light). **Workspace plugins** live in the example workspace that uses them, so adding a new third-party provider never requires editing `packages/`. See [§ Authoring a workspace plugin](#authoring-a-workspace-plugin) below.

## `ProviderDescriptor` interface

```ts
// Source: examples/playground/app/providers/types.ts
export interface ProviderDescriptor {
  /** Stable id used in the wire payload (provider.id) and on the server. */
  id: string;
  /** Visible option label in the Providers dropdown. */
  label: string;
  /** Short description shown below the dropdown or as a tooltip. */
  description: string;
  /** Config fields rendered when this provider is selected. */
  configFields: ProviderConfigField[];
  /** If true, the provider is shown but cannot be selected yet. */
  disabled?: boolean;
}
```

Disabled entries render with the HTML `disabled` attribute — the user sees the option but cannot pick it.

## `ProviderConfigField` types

```ts
export type ProviderConfigFieldType = 'text' | 'path';

export interface ProviderConfigField {
  /** Key under `provider.config[key]` on the wire. */
  key: string;
  /** Visible label above the input. */
  label: string;
  /** Render hint — currently only `text` and `path` are implemented. */
  type: ProviderConfigFieldType;
  /** Default value when none is stored. */
  default: string;
  /** Placeholder shown inside the empty input. */
  placeholder: string;
  /** Optional helper text below the input. */
  help?: string;
}
```

`type: 'path'` is functionally identical to `'text'` today, reserved for a future path-picker UI.

## `ProviderWirePayload` wire shape

The provider block carried on every `chat.message` frame:

```ts
export interface ProviderWirePayload {
  id: string;
  /** Free-form config keyed by ProviderConfigField.key. */
  config: Record<string, string>;
}
```

What arrives on the WebSocket:

```ts
{
  v: 1, channel: '__chat__', type: 'chat.message',
  payload: {
    prompt: 'Show me San Francisco weather',
    registry: 'primevue',
    provider: { id: 'claude-code', config: { cliPath: '/opt/homebrew/bin/claude' } },
  },
  seq: 0
}
```

The server's chat handler unpacks `payload.provider.id`, calls `getProviderAdaptor(id)`, and forwards `config` to the adapter's `resolveBinary()` + `buildArgs()`. The adapter's `id` and `label` are server-side metadata — never sent on the wire.

## How the playground selects + persists providers

The `useProviders` composable ([`examples/playground/app/composables/useProviders.ts`](https://github.com/your-org/genicui)) is a singleton — module-level `ref`s shared across every consumer. State persists to:

```text
localStorage key:  genicui-playground:providers:v2
value (JSON):      { selectedProviderId: string, config: Record<string, Record<string, string>> }
```

The `:v2` suffix lets the playground evolve the persisted shape without colliding with the legacy key. Hydration is idempotent; corrupted JSON is swallowed, leaving defaults in place. A deep `watch` persists every change after the first hydration so the initial mount doesn't overwrite persisted state.

`getWirePayload()` is the assembly point — merges persisted values over field defaults:

```ts
function getWirePayload(): ProviderWirePayload {
  return { id: selectedProviderId.value, config: getConfig() };
}
```

## How the server spawns the CLI

The server-side adapter (`packages/server/src/chat/providers/claude-code.ts`) is the only place that knows how to spawn the CLI:

```text
1. Chat handler unpacks payload.provider → { id, config }
2. getProviderAdaptor(id) → ClaudeCodeAdaptor
3. resolveBinary(config) → '/opt/homebrew/bin/claude'
   (priority: config.cliPath → $GENICUI_CLAUDE_BIN → 'claude' on $PATH)
4. buildArgs({ resumeId }) → ['--print', '--output-format', 'stream-json', ...]
5. Bun.spawn(binary, args) — handler owns the lifecycle
6. Each stdout line → parseLine(line) → ChatEvent
7. Chat handler wraps ChatEvent in a chat.event frame on __chat__
```

`resolveBinary`, `buildArgs`, and `parseLine` are pure functions — the whole adapter is testable without spawning a real process. The chat handler owns `Bun.spawn` (PID, stdout streaming, stderr buffering, exit handling) so cross-cutting concerns live in one place. `--resume <sessionId>` is passed on subsequent turns; `--mcp-config` tells the CLI where to find the GenicUI MCP server (default: `<repo>/.mcp.json`).

::callout{type="info"}
**Adapters return argv; the chat handler owns the spawn.** This split keeps each adapter trivial to unit-test and centralizes process lifecycle in one place.
::

## Authoring a workspace plugin

The framework's two built-in adapters (`claude-code`, `codex`) live in `packages/server/src/chat/providers/`. They are tolerable first-party entries — small, env-light, no fixture weight. **Every other provider — including HTTP-shaped ones that ship fixtures, bearer tokens, and a dozen TypeBox schemas — should NOT live in core.** See §7 for the VaahStore worked example.

Instead, **each example workspace ships its own plugin API and its own plugins**, scoped to the workspace. `@genicui/core` and `@genicui/server` stay provider-free for third-party adapters. This section is the reference for authoring a plugin in a workspace.

### §1 · The provider-free framework

`@genicui/core` and `@genicui/server` export zero third-party provider symbols. The framework's job is to define the `ProviderAdaptor` interface, the `ProviderWirePayload` shape, and the chat-handler dispatch logic. **Plugins live in example workspaces**, not in `packages/`.

Concretely: when a new example workspace (`examples/<workspace>/`) wants to ship its own chat provider — for example, to expose a third-party HTTP API as agent-callable tools — it copies the in-workspace plugin pattern. No edit to `packages/` is required. The workspace isolation script (`scripts/check-isolation.sh`, see §5) gates the rule.

### §2 · `defineProvider(...)` — the template

Each workspace exposes its own `defineProvider` factory at `examples/<workspace>/server/providers/registry.ts`. The factory is a pure function that returns a `ProviderPluginManifest` — a description of the plugin, NOT a constructor invocation:

```ts
// examples/<workspace>/server/providers/boot.ts
import { defineProvider, registerProvider, unregisterProvider } from './registry.js';
import { createMyProvider, MyProviderConfigSchema } from './<name>/runtime/index.js';

export function bootMyProvider(env: NodeJS.ProcessEnv = process.env): void {
  // HMR-safe re-registration — Nuxt reloads this file on every code change.
  unregisterProvider('<id>');

  registerProvider(defineProvider({
    id: '<id>',
    label: '<display name>',
    configSchema: MyProviderConfigSchema, // TypeBox with additionalProperties: false
    requiresIsolation: false,
    factory: () => createMyProvider(env),
  }));
}

// Idempotent — call once at workspace boot.
bootMyProvider();
```

The chat handler's 5-method consumer surface (`id, label, resolveBinary, buildArgs, parseLine`) is unchanged across the move. Workspace plugins may expose additional methods on the `ProviderAdaptor` return value (e.g. `callTool`, `scrubWithToken`, `liveMode` for HTTP-shaped providers), but those are consumed by the **workspace's** own agent/journey code — never by the framework's chat handler.

### §3 · F14 wrap-at-registration — the contract

Every plugin must satisfy the [F14 trust-boundary](/concepts/trust-boundary) contract at **registration time**, not at call time. The workspace's `registerProvider(...)` composes the F14 primitives from the workspace-local `validation/` barrel:

```ts
// examples/<workspace>/server/providers/registry.ts (excerpt)
import {
  rejectOpenSchemas,          // F14-AC3
  validateToolInput,          // F14-AC2
  stripProtoKeys,             // F14-AC1
} from './validation/index.js';

export function registerProvider(spec: ProviderPluginSpec | ProviderPluginManifest): void {
  const manifest = 'factory' in spec ? spec : defineProvider(spec);

  if (REGISTRY.has(manifest.id)) throw new DuplicateProviderError(manifest.id);

  // F14-AC3 — reject open schemas at registration time.
  rejectOpenSchemas(manifest.configSchema, `/providers/${manifest.id}/configSchema`);

  // Probe the factory once to verify shape + bearer-scrub contract.
  const probe = manifest.factory();
  if (!probe || typeof probe !== 'object' || typeof probe.id !== 'string') {
    throw new ProviderShapeError(manifest.id, 'factory must return an object with an `id` string');
  }
  if (manifestRequiresBearerScrub(manifest) && typeof probe.scrubWithToken !== 'function') {
    throw new BearerScrubMissingError(manifest.id);
  }

  REGISTRY.set(manifest.id, { id: manifest.id, manifest, adaptor: probe, worker: null });
}
```

The workspace keeps its own shallow copies of `stripProtoKeys`, `rejectOpenSchemas`, and `validateToolInput` under `server/providers/validation/`. They mirror the authoritative implementations in `packages/server/src/validation/` verbatim, but re-importing them would require a workspace dependency on `@genicui/server`'s internal subpaths — and that leaks the framework into a workspace that should stay provider-free. The shallow-copy rule is enforced by `scripts/check-isolation.sh` (§5).

Four rejection paths fire before `registerProvider` returns:

- **`additionalProperties: true`** in any `configSchema` → reject with `RegistryValidationError` (F14-AC3, mirrors `packages/server/src/validation/registry-validation.ts`).
- **HTTP-shaped manifest + factory missing `scrubWithToken`** → reject with `BearerScrubMissingError` (workspace-local code `-32010 plugin_bearer_scrub_missing`).
- **Duplicate id** → reject with `DuplicateProviderError`.
- **Factory returns `null` / non-object / object without `id: string`** → reject with `ProviderShapeError`.

The HTTP-shape heuristic (`manifestRequiresBearerScrub`) matches these top-level property names in `configSchema`: `bearer`, `bearerToken`, `Authorization`, `token`, `apiKey`, `api_key` (case-insensitive). When matched, the factory's output must expose a `scrubWithToken(value)` method.

These contracts are tested with a 10K fast-check property run over random `defineProvider(...)` specs (see the workspace's `__tests__/wrap-at-registration.test.ts`).

::callout{type="warning"}
**Bearer scrubbing is closure-bound to the instance, not module-global.** Two plugins with different bearer tokens must not share a scrubber — otherwise token A could leak into provider B's logs. The factory closure pattern in §2 enforces this — `createMyProvider(env)` is called fresh inside `factory: () => createMyProvider(env)`, so each registration gets a new scrubber bound to the env-supplied token.
::

### §4 · Discovery — boot file + `discoverWorkspaceProviders`

Each workspace declares its plugins in **two complementary ways**:

1. **Explicit boot file** at `examples/<workspace>/server/providers/boot.ts`. Calls `registerProvider(defineProvider({ ... }))` once at workspace start, with `unregisterProvider(id)` first to handle HMR reloads. Wired into Nuxt via `server/plugins/00-boot-providers.ts` which is auto-loaded by Nuxt's server plugin convention.

2. **`discoverWorkspaceProviders(workspaceRoot)` helper** at `examples/<workspace>/server/providers/registry.ts`. Walks `<workspaceRoot>/server/providers/*/define.ts` and auto-registers each plugin whose default export is a `ProviderPluginManifest`. Returns `WorkspaceDiscoveryResult = { manifests: ProviderPluginManifest[]; warnings: string[] }` — failed registrations (syntax errors, F14 violations) populate `warnings[]` without crashing boot. **Opt-in**: the workspace's `boot.ts` may call it instead of (or after) the explicit registrations; plugin authors can replace a single explicit registration with `await discoverWorkspaceProviders(import.meta.dir + '/../..')` for a hands-off setup.

The workspace's `package.json` declares the framework version it targets and lists the boot file:

```json
{
  "name": "genicui-<workspace>",
  "engines": { "genicui": "^0.1.0" },
  "genicui": {
    "plugins": ["./server/providers/boot.ts"]
  }
}
```

The `genicui.plugins` field is **optional** — same discoverable behavior either way. Listed here so plugin authors can read the boot-time intent at a glance.

### §5 · Workspace isolation gate

Every plugin workspace ships `scripts/check-isolation.sh`, wrapped as the `bun --filter <workspace> check-isolation` script. The gate ensures no future contributor can re-introduce a `packages/` edit without a failing build:

```bash
#!/usr/bin/env bash
# examples/<workspace>/scripts/check-isolation.sh
#
# Whitelist-compare — does not use git diff pathspec exclusions
# because deletions report basename-only (`<name>.test.ts`), not the
# full path (`__tests__/<name>.test.ts`), and `:!foo` does not filter
# deletions in rename-tracking mode.
set -euo pipefail
ROOT=$(git rev-parse --show-toplevel)
cd "$ROOT"

WHITELIST=$(cat <<'EOF'
packages/server/src/chat/providers/<name>.ts
packages/server/src/chat/providers/<name>.test.ts
packages/server/src/chat/providers/__fixtures__/<name>
packages/server/src/chat/providers/registry.ts
EOF
)

CHANGED=$(mktemp)
git diff --name-only develop..HEAD -- packages/ | sort > "$CHANGED"
UNEXPECTED=$(comm -23 "$CHANGED" <(echo "$WHITELIST" | sort))

if [ -n "$UNEXPECTED" ]; then
  echo "FAIL: edits detected under packages/ (outside the plugin move zone):" >&2
  echo "$UNEXPECTED" >&2
  rm -f "$CHANGED"
  exit 1
fi

# Adjacent isolation zones — the other example workspaces + root
# package.json must be untouched.
git diff --quiet develop..HEAD -- examples/playground/ examples/docs/ package.json \
  || { echo "FAIL: edits detected in adjacent isolation zones"; exit 1; }

echo "[check-isolation] workspace isolation holds"
```

Four whitelisted paths cover the **intended** `packages/` edits when the plugin's source is moving out of core:
- the `<name>.ts` deletion (move target);
- the `<name>.test.ts` deletion (test moves with source);
- the `__fixtures__/<name>/` deletion (fixtures move with source);
- the `registry.ts` removal of the now-dangling `./<name>.js` import + the corresponding Map entry (without it `@genicui/server` cannot resolve).

For a greenfield plugin (no source to move out of core) the whitelist is empty — `comm` produces zero unmatched lines and the gate passes trivially.

Every plugin task's completion criteria invokes `bun --filter <workspace> check-isolation` after each commit.

### §6 · Worker-isolation opt-in

Some plugins carry credentials or untrusted subprocess lifecycles that should be sandboxed. The workspace's `ProviderPluginManifest` exposes `requiresIsolation: boolean`:

```ts
defineProvider({
  id: '<id>',
  // ...
  requiresIsolation: true, // <-- opt in
});
```

When `requiresIsolation: true`, the workspace's `getProviderAdaptor(id)` lazily routes the factory output through a Worker thread. Bun inline-source is the current implementation seam — Bun doesn't support `new Worker(codeString)` like Node.js, so the worker is spawned via `URL.createObjectURL(new Blob([src], {type:'application/javascript'}))`. A follow-up task can replace this stub with the real `node:worker_threads.Worker` + `MessagePort` plumbing — the contract surface (`getProviderAdaptor(id)` returns a synchronous-looking `ProviderAdaptor`) is unchanged.

Default off. HTTP-shaped plugins that only need a bearer-scrub closure (§3) typically ship with `requiresIsolation: false`. The opt-in's **contract** is tested with a fake-isolated stub and a real Worker round-trip (see the workspace's `__tests__/worker-isolation.test.ts`) — no second real plugin required.

::callout{type="info"}
**Why opt-in, not mandatory.** Mandatory worker isolation adds a JSON marshalling cost to trivial CLI tokens (`Bun.spawn` is already isolated via OS process). Skipping it would make future bearer-bearing plugins hard to defend security-wise. The opt-in lets each plugin author make the cost/benefit choice at registration time.
::

### §7 · Worked example — VaahStore end-to-end

The VaahStore workspace plugin is the canonical reference for the in-workspace pattern. Reading it top-to-bottom mirrors §1-§6:

- **Adapter source**: [`examples/playground-ecommerce/server/providers/vaahstore/runtime/index.ts`](https://github.com/your-org/genicui/tree/main/examples/playground-ecommerce/server/providers/vaahstore) — exports `createVaahstoreProvider(env)`, `VaahstoreProviderAdaptor` class, `VAAHSTORE_TOOL_SCHEMAS` (13 TypeBox schemas), `readVaahstoreEnv(env)`, `makeBearerScrubber(token)`. The runtime directory follows Bun's `server/` convention — the entry file is at `runtime/index.ts` (not the older `vaahstore.ts`) because future plugins may add sibling files (e.g. `worker-entry.ts`).
- **Boot file**: `examples/playground-ecommerce/server/providers/boot.ts` — calls `unregisterProvider('vaahstore')` first (HMR-safe) then `registerProvider(defineProvider({..., factory: () => createVaahstoreProvider(env)}))`. Maps to §2 (template) and §4 (boot file).
- **Nuxt server plugin**: `examples/playground-ecommerce/server/plugins/00-boot-providers.ts` — imports `boot.ts` and logs `listProviderIds()`. Nuxt 4 auto-loads files under `server/plugins/`. Maps to §4 (Nuxt wiring).
- **13 TypeBox schemas** for the VaahStore endpoints (`list_products`, `get_product`, `get_variations`, `check_stock`, `create_cart`, `add_to_cart`, `list_shipping`, `list_payment_methods`, `create_order`, `create_address`, `track_order`, `sign_up_guest`, `attach_user_to_cart`) live in `runtime/index.ts`. Fixture-mode (`VITE_VAAHSTORE_LIVE=0`, the default) reads from `examples/playground-ecommerce/__fixtures__/vaahstore/`. Maps to §3 (F14 wrap on every schema) and §1 (workspace-owned, not in `packages/`).
- **Workspace-local validation primitives**: `server/providers/validation/` — `strip-proto-keys.ts`, `registry-validation.ts`, `schema-validation.ts`, `index.ts`. Shallow copies of `packages/server/src/validation/`, marked with `TODO(M5.x)` notes about a future merge. Maps to §3 (the validation barrel).
- **Tests**: 43 inherited tests travel unchanged from the original `packages/server/src/chat/providers/__tests__/vaahstore.test.ts` location (just an updated import path: `'../vaahstore/runtime/index.js'`). New contract tests (validation, registry round-trip, F14 wrap-at-registration, worker-isolation, discovery) sit alongside in `__tests__/`. **Total: 89 tests across 6 files, all passing.** Maps to §3 + §5 + §6.
- **Workspace docs**: `examples/playground-ecommerce/README.md` documents the workspace layout. `examples/playground-ecommerce/docs/plugin-architecture.md` is the workspace-level reference (mirrors this page).

The VaahStore worked example proves that **adding a third-party HTTP-shaped chat provider does not require any edit to `@genicui/core`, `@genicui/server`, or root `package.json`**. The 731-line adapter + 43 tests + 13 fixtures travel unchanged through the move — only the file location changes.
