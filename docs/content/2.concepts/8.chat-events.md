The chat overlay sits beside the AG-UI event vocabulary documented in [Events](/concepts/events). Where AG-UI events describe what a *mounted component* does, chat events describe what an *LLM provider* (Claude Code today, codex tomorrow) is doing inside the GenicUI server. This page covers the seven `chat.event.type` values that ride on the reserved `__chat__` channel.

## Why chat events exist

GenicUI's chat feature is provider-agnostic at the wire boundary but CLI-specific under the hood. The current `claude-code` provider adaptor ([`packages/server/src/chat/providers/claude-code.ts`](https://github.com/your-org/genicui)) spawns the `claude` CLI with `--output-format stream-json` and parses its stdout line-by-line. The CLI emits roughly a dozen different envelope shapes — `assistant`, `user`, `system`, `tool_use`, `tool_result`, `result`, plus verbose-mode `message.content[]` arrays and compact-mode `text`/`data` shapes.

That vocabulary is rich but CLI-specific. A Vue playground client and a CLI chatbot and a future Python desktop client should all consume the same shape. So the adaptor maps each CLI envelope to one of **seven** stable types before broadcasting. New providers (codex, gemini-cli) must emit the same seven — that's the wire contract.

## End-to-end connection flow

The full chain — from a user typing a prompt to a chat event landing in a client — looks like this:

```text
Developer machine                                       Server (genicui-server)
─────────────────                                       ────────────────────

claude mcp add --transport http genicui http://localhost:3040/mcp
                                │
                                ▼
                  Claude Code reads .mcp.json at startup
                                │
                                ▼
        ┌───────────────────────────────────────────────┐
        │  Claude Code spawns its MCP client            │
        │  → POST /mcp  (initialize)                    │
        │  → POST /mcp  (tools/list)                    │
        │     discovers 4 tools:                         │
        │       • find_ui_component                      │
        │       • render_component                       │
        │       • update_component                       │
        │       • subscribe_to_events                   │
        └───────────────────────┬───────────────────────┘
                                │   user types "show me SF weather"
                                ▼
        ┌───────────────────────────────────────────────┐
        │  Claude Code invokes tools as needed:         │
        │   find_ui_component  → { name: "CityPicker" } │
        │   render_component   → componentId            │
        │   subscribe_to_events → subscriptionId        │
        └───────────────────────┬───────────────────────┘
                                │
                                ▼  CLI stdout stream-json
        packages/server/src/chat/providers/claude-code.ts
                                │  mapStreamJsonEvent(parsed) → ChatEvent
                                ▼
        ┌───────────────────────────────────────────────┐
        │  WebSocket frame, channel = '__chat__'        │
        │                                               │
        │    { v: 1,                                    │
        │      channel: '__chat__',                     │
        │      type: 'chat.event',                      │
        │      payload: { event: ChatEvent },          │
        │      seq: <N> }                               │
        │                                               │
        │    where ChatEvent.type ∈ {                   │
        │      ai_text, tool_call, tool_result,         │
        │      status, error, stderr, user_event        │
        │    }                                          │
        └───────────────────────┬───────────────────────┘
                                │
                                ▼
        Client (e.g. examples/playground)
        useChat().handleEvent(frame) → switch (evt.type) → render
```

The key insight: **the four MCP tools** (`find_ui_component`, `render_component`, `update_component`, `subscribe_to_events`) and **the seven chat events** live on opposite sides of the same connection. Tools flow agent → server (MCP `tools/call`). Chat events flow server → agent's hosting client (WebSocket `chat.event`). A complete UI session interleaves both.

## The seven event types

Each row below documents the type, direction, payload shape, and the server file that emits it.

| `type` | Direction | `data` payload | Emitted by |
|--------|-----------|----------------|------------|
| `ai_text` | server → client | `{ text: string }` | `claude-code.ts::mapStreamJsonEvent` (both compact `text` envelopes and verbose `assistant` content blocks) |
| `tool_call` | server → client | `{ id: string, name: string, input \| args: object }` | `claude-code.ts::mapStreamJsonEvent` (compact `tool_use`) + `parseAssistantEvent` (verbose `tool_use` blocks) |
| `tool_result` | server → client | `{ id: string, name?: string, result: string }` | `claude-code.ts::mapStreamJsonEvent` (compact `tool_result`) + `parseUserEvent` (verbose `user` message with `tool_result` content) |
| `status` | server → client | `{ status: 'init' \| 'thinking' \| 'complete' \| 'task_started' \| 'task_progress' \| 'task_completed', ... }` | `claude-code.ts::mapStreamJsonEvent` (`result`) + `parseSystemEvent` (`init`, `task_*`) |
| `error` | server → client | `{ error \| message: string }` | `claude-code.ts::mapStreamJsonEvent` (compact `error`) + `parseSystemEvent` (system-with-error fallback) |
| `stderr` | server → client | `{ text: string }` | Surfaced from `ParsedLine.kind === 'stderr'`; chat handler buffers stderr and emits it as a `chat.event` of this type |
| `user_event` | server → client | `{ componentId: string, name: string \| null, action: string, payload: object }` | Server-side synthesizer, inserted after a chat-embedded component interaction (F43) |

::callout{type="info"}
**Field-name variance:** `tool_call` accepts either `input` (verbose-mode envelope, Anthropic SDK canonical) or `args` (compact-mode CLI shorthand). The client `useChat.handleEvent` reads both; the server emits whichever the CLI provided.
::

## Per-type payload reference

### `ai_text`

Visible assistant prose. The server concatenates consecutive chunks on the client; do not assume the client receives the full reply in one frame. Compact-mode `text` envelopes and verbose-mode `assistant` content blocks both produce this type — thinking blocks are dropped.

### `tool_call`

The agent is invoking a tool. The `id` is optional from some CLIs; the client falls back to the most recent running call when no id matches. The MCP wrapper prepends `mcp__<server>__` to the tool name when the tool came from an MCP server; the client preserves whichever form the agent sent.

```ts
{
  type: 'tool_call',
  data: {
    id: 'toolu_01X9Z',
    name: 'render_component',                  // bare or mcp__<server>__<tool>
    input: { name: 'DataTable', props: {...} } // or `args` — see field-name variance
  }
}
```

### `tool_result`

A tool returned. Match by `id` if present; otherwise the client attaches to the last `running` entry. `result` is always a string at the wire level — the CLI emits raw JSON-stringified output; clients JSON-parse to type it.

### `status`

Progress markers. Most clients ignore these; they're useful for typing indicators and emitting usage stats. Subtypes: `init` (session start, carries `sessionId` for `--resume`), `task_started`, `task_progress`, `task_completed`, `complete` (end-of-turn with usage stats).

### `error`

Non-fatal error. If a tool call is currently running, the client attaches the error to that tool's accordion. Otherwise it falls back to prose. Client accepts both `{ error: string }` and `{ message: string }` shapes.

### `stderr`

Provider stderr (the CLI's diagnostic output). Clients typically log this and do not surface it in the UI — useful for debugging tool-call failures without polluting the user-visible reply.

### `user_event`

A chat-embedded component fired an interaction. The server synthesizes a follow-up turn but first inserts this `user_event` so the chat history shows a click bubble before the next assistant response lands. The client renders it as a synthetic user entry with prompt `[click] <action> on <name> {<detail>}` — a click bubble, not a typed prompt.

## Wire envelope

Every chat event travels inside a standard [frame envelope](/concepts/frames) on the `__chat__` channel:

```ts
{
  v: 1,
  channel: '__chat__',
  type: 'chat.event',
  payload: {
    event: {
      type: 'ai_text',          // one of the 7
      data: { text: '...' }
    }
  },
  seq: 42                      // monotonic per channel
}
```

The `chat.event` wrapper is the only `type` that appears on `__chat__`. Clients should switch on `payload.event.type` to dispatch to per-type handlers. Other frames on `__chat__` include `chat.message` (client → server, the prompt), `chat.response` (server → client, the legacy echo path), `chat.complete`, and `chat.error`.

## Who emits what

| File | Emits |
|------|-------|
| `packages/server/src/chat/providers/claude-code.ts::mapStreamJsonEvent` | `ai_text`, `tool_call`, `tool_result`, `status` (`result`), `error` |
| `packages/server/src/chat/providers/claude-code.ts::parseAssistantEvent` | `ai_text` (verbose text blocks), `tool_call` (verbose tool_use blocks) |
| `packages/server/src/chat/providers/claude-code.ts::parseUserEvent` | `tool_result` (verbose user message with tool_result content) |
| `packages/server/src/chat/providers/claude-code.ts::parseSystemEvent` | `status` (`init`, `task_started`, `task_progress`, `task_completed`), `error` (system-with-error fallback) |
| `packages/server/src/chat/handler.ts` (chat handler) | `stderr` (from `ParsedLine.kind === 'stderr'`), `user_event` (synthesized on chat-embedded component events) |

::callout{type="warning"}
**Adding a new provider?** Your adaptor MUST emit the same seven types — the wire contract is the seven, not the CLI's raw vocabulary. New providers can add types via a separate extension channel, but the seven listed above are non-negotiable for client compatibility.
::

## How clients handle it

Pseudocode from [`examples/playground/app/composables/useChat.ts::handleEvent`](https://github.com/your-org/genicui):

```ts
function handleEvent(frame: unknown): void {
  const evt = frame.payload?.event;
  switch (evt.type) {
    case 'ai_text':     appendToResponse(evt.data.text); break;
    case 'tool_call':   toolCalls.push(makeEntry(evt.data)); break;
    case 'tool_result': attachResult(toolCalls, evt.data); break;
    case 'error':       attachErrorToRunningCall(evt.data); break;
    case 'stderr':      console.warn('[chat] stderr:', evt.data.text); break;
    case 'user_event':  pushSyntheticUserBubble(evt.data); break;
    case 'status':      /* ignore — UI doesn't render progress markers */ break;
  }
}
```

A few invariants worth highlighting:

- **`tool_call` then `tool_result` is paired.** The client matches by `id` if present, else attaches to the last `running` entry.
- **`error` prefers tool context.** If a tool call is currently running, the error attaches to that tool. Only if no tool is running does the client append to the prose.
- **`status` is informational.** Clients ignore most subtypes; they exist for observability and future UI affordances (typing indicators, usage meters).
- **`user_event` is append-only.** It runs even when history is empty so a synthetic bubble still appears if the user clicked a component before sending any prompt.

## Why these aren't AG-UI events

The 14 AG-UI event types (`STATE_SNAPSHOT`, `STATE_DELTA`, `COMPONENT_MOUNTED`, etc.) describe the **lifecycle of a mounted component**. They travel on per-component channels. Chat events describe the **lifecycle of an LLM provider turn**. They travel on the reserved `__chat__` channel. The two vocabularies are deliberately separate:

- A client that only renders components (no chat) needs only AG-UI events.
- A chat-only client (CLI bot) needs only the seven chat events.
- A full GenicUI client consumes both, but on different channels.

Putting chat events on AG-UI would force every component client to know about LLM streaming. Putting AG-UI events on `__chat__` would force every chatbot to know about component mounting. The split is intentional.
