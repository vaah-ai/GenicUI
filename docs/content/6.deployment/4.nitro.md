Drop GenicUI into a Nuxt app as a first-class module. The `nuxt-genicui` module wires the same `@genicui/server` runtime into the host app at `/api/ws`, so GenicUI shares the host's origin, the host's auth middleware, and the host's infrastructure.

This page is a **landing** — it links to the M6-T4 deep dive that owns the module, the devtools panel, and the auth-from-env wiring. If you've already decided on a Nitro binding, jump to the M6-T4 task file; otherwise compare against the [overview](/deployment/overview) options.

## When to pick Nitro

Three signals point at the binding over a standalone target:

- **Nuxt is your primary app.** You're already deploying a Nuxt site — adding a second service means CORS, origin validation, and infrastructure duplication that the binding removes by construction.
- **Same-origin wins.** WebSocket upgrades don't require CORS when they share an origin with the page. The host app's auth middleware can gate the WS endpoint.
- **Shared observability.** Logs, traces, and request metrics stay in your existing aggregator. No second set of dashboards.

## Architecture

The module auto-generates a Nitro WebSocket handler at `server/api/ws.ts`. The handler delegates the WebSocket lifecycle to `@genicui/server/nitro`, which uses the same core runtime as the Workers and Bun adapters.

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-genicui', '@genicui/client'],
  genicui: {
    apiKey: process.env.GENICUI_API_KEY, // read from env, never checked in
    surface: 'default',
  },
});
```

```ts
// auto-generated at build: server/api/ws.ts
import { mountGenicUIForNitro } from '@genicui/server/nitro';

export default defineWebSocketHandler({
  open(peer) {
    mountGenicUIForNitro({ peer, config: useRuntimeConfig().genicui });
  },
  message(peer, message) {
    // delegated to @genicui/server core
  },
  close(peer) {
    // cleanup
  },
});
```

::note
**Why same-origin matters for WebSocket.** Browsers refuse cross-origin WS upgrades without explicit permission (CORS doesn't apply to WS, but mixed-content and origin checks do). A same-origin `/api/ws` keeps your auth cookies and CSRF protections intact.
::

## Prerequisites

- Nuxt `3.x` or `4.x` with Nitro
- `pnpm add nuxt-genicui @genicui/server @genicui/client`
- A `gnc_live_<32>` API key in `GENICUI_API_KEY` (read via `process.env` at boot)
- Nitro's experimental WebSocket support enabled (default in Nitro ≥ 2.10)

## Trade-offs

::callout{type="warning"}
**What you give up by choosing the Nitro binding:**

- **Tied to the Nuxt release cycle.** A Nuxt major version bump can require a `nuxt-genicui` release. The Workers and Bun adapters are decoupled from any framework's cadence.
- **Cannot run on Cloudflare Workers.** Nitro's WebSocket handler currently targets Node, Bun, and the Vercel/Netlify adapters. There is no Workers preset today.
- **Shared fate with the host app.** If the host app crashes, GenicUI goes down with it. Standalone deployments isolate failures better.
- **In-memory state by default.** Sessions live in the host process. For multi-instance Nuxt hosts you'll need a shared store (Postgres, Redis) — wire it yourself.
- **Devtools panel is part of the host UI.** F64-AC3 ships a sessions panel in `nuxt-devtools`. If you prefer a separate admin tool, the Cloudflare or Bun standalones expose a JSON admin API instead.

If any of these is a hard blocker, the [Cloudflare Workers](/deployment/cloudflare) target or the [Bun self-host](/deployment/bun-self-host) may be a better fit.
::

## Operational tooling

- `pnpm dev` — local Nuxt dev server with HMR for GenicUI components
- `pnpm build` — produce `.output/server` for any Nitro-compatible host (Vercel, Netlify, CF Pages, Node)
- `pnpm preview` — smoke-test the production bundle
- `nuxt-devtools` — GenicUI sessions panel lives under the Devtools tab
