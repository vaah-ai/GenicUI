Run GenicUI as a single OS binary with no external runtime install. Two paths share the same `@genicui/server/bun` adapter: `bun run start` for fast iteration, and `bun build --compile` for a static binary you can ship to bare hosts and containers.

This page is a **landing** — it links to the M6-T2 deep dive that owns the binary, sizing, and cold-start tests. If you've already decided on Bun, jump to the M6-T2 task file; otherwise skim the [overview](/deployment/overview) decision matrix first.

## When to pick Bun

Three signals point at self-host over Cloudflare:

- **You already operate servers.** You have a deploy target, an SSH / Ansible / systemd story, or a Kubernetes cluster — and you'd rather not introduce a third vendor.
- **One region is fine.** You're serving a single geography, an internal tool, or a backend service that isn't user-facing.
- **Dev and CI parity.** You want the local process to be the same artifact the test suite and CI smoke test exercise.

## Two ways to run

::tabs
:::tabs-item{icon="i-lucide-terminal" label="Dev / iteration"}

Run the source directly — fastest iteration loop, full HMR, no build step:

```bash
bun install
bun run start
# Server running at http://localhost:8080
```

The entry point wires `@genicui/server/bun` into an Elysia app:

```ts
import { Elysia } from 'elysia';
import { mountGenicUIForBun } from '@genicui/server/bun';

const app = new Elysia()
  .get('/health', () => ({ status: 'ok' }))
  .use(mountGenicUIForBun({
    apiKey: process.env.GENICUI_API_KEY,
    port: Number(process.env.GENICUI_PORT ?? 8080),
  }))
  .listen({ port: 8080, hostname: '0.0.0.0' });
```

::

:::tabs-item{icon="i-lucide-package" label="Compiled binary"}

Compile to a single binary — host with no Bun install, ship as a container artifact, drop into a Kubernetes pod:

```bash
bun build src/server.ts --compile --outfile genicul
./genicui
```

The target binary is self-contained: `oven/bun:1.2` and `node:alpine` base images both run it. For a minimal Dockerfile:

```dockerfile
FROM oven/bun:1.2
WORKDIR /app
COPY package.json bun.lock ./
RUN bun install --frozen-lockfile
COPY . .
RUN bun build src/server.ts --compile --outfile /usr/local/bin/genicui
EXPOSE 8080
CMD ["genicui"]
```

## Prerequisites

- Bun `1.2` or newer — `curl -fsSL https://bun.sh/install | bash`
- For binary compilation, a Linux build host that matches your deploy target
- A `gnc_live_<32>` API key — `openssl rand -hex 16`
- A reverse proxy for TLS (Caddy, Nginx, or Traefik) — GenicUI speaks plain HTTP/WS behind the proxy

## Trade-offs

::callout{type="warning"}
**What you give up by choosing Bun self-host:**

- **You own ops.** Process supervision, log shipping, secret rotation, OS patching, and capacity planning are on you. A `systemd` unit or a k8s `Deployment` is your job.
- **No auto-scaling.** Horizontal scale is manual (or scripted) — add capacity before traffic spikes, not after.
- **Single region by default.** Multi-region requires running the binary in N regions and putting a smart load balancer (or DNS-based geo) in front.
- **In-memory state by default.** The MVP store loses sessions on restart. Wire [Postgres or SQLite](https://bun.sh/docs/api/sqlite) yourself, or accept the loss.
- **Cold start = 0ms only because you're always warm.** If you autoscale to zero, the first request pays the boot cost. Cloudflare's hibernation model avoids this by design.

If any of these is a hard blocker, the [Cloudflare Workers](/deployment/cloudflare) target or the [Nitro binding](/deployment/nitro) may be a better fit.
::

## Operational tooling

- `bun run start` — local iteration
- `bun build src/server.ts --compile --outfile genicul` — produce a binary
- `ls -lh genicul` — verify size budget (F62-AC2 requires <50MB)
- `systemctl status genicul` — process supervision
- `curl http://localhost:8080/health` — readiness probe

The [production checklist](/guides/production) covers the post-deploy gate (CORS, observability, log scrubbing, rate-limit hooks) that applies once your binary is behind a reverse proxy.
