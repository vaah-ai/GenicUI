This guide maps the three most common inbound paths onto GenicUI. For each, we show the wire-level diff, the surface-level diff, and the migration risk. **Migration is the highest-value guide in this section** — it converts evaluators into adopters. Spend the time to walk the path that matches your starting point end-to-end.

::callout{type="info"}
**All three paths keep the agent-side unchanged.** The wire protocol GenicUI ships is a superset of AG-UI events; any agent already emitting AG-UI events (which OpenAI Apps SDK, CopilotKit, and the MCP Apps proposal all do) keeps its core loop. You're swapping the *surface* and the *transport hardening* — not the reasoning loop.
::

## Inbound overview

| From | Surface diff | Transport diff | Effort |
|---|---|---|---|
| **MCP Apps** | `resources/list` + `resources/read` → `find_ui_component` + `render_component` | None (Streamable HTTP stays) | Small |
| **OpenAI Apps SDK** | `_meta['openai/outputTemplate']` → GenicUI registry | Same `_meta` envelope; GenicUI runs as a runtime adapter | Medium |
| **CopilotKit** | React custom renderers → GenicElement + closed Shadow DOM | AG-UI native already — wire stays | Medium |

## From MCP Apps

MCP Apps is the proposal that uses MCP `resources` to vend UI templates. GenicUI replaces the resource layer with its first-class `find_ui_component` + `render_component` tools and keeps everything else.

### Wire-level diff

::tabs
:::tabs-item{icon="i-lucide-x" label="MCP Apps"}
```json
// Request
{"method":"resources/list"}
// Response
{"resources":[{"uri":"ui://components/data-table","mimeType":"application/json"}]}

// Render
{"method":"resources/read","params":{"uri":"ui://components/data-table"}}
```
:::

:::tabs-item{icon="i-lucide-check" label="GenicUI"}
```json
// Request
{"method":"tools/call","params":{"name":"find_ui_component","arguments":{"query":"data table","topK":1}}}
// Response
{"result":{"components":[{"name":"data-table","uri":"ui://components/data-table@1.0.0"}]}}

// Render
{"method":"tools/call","params":{"name":"render_component","arguments":{"name":"data-table","props":{"rows":[...],"columns":[...]}}}}
```
:::
::

### Migration steps

::steps{level="3"}
#### Replace `resources/list` polling with `find_ui_component`

Search is now query-driven, not enumeration-driven. Drop the polling loop and use the tool inline.

#### Replace `resources/read` with `render_component`

The render path becomes a typed tool call. Validate against the registry's `propsSchema` *before* sending — the server's trust boundary will reject extra keys anyway.

#### Adopt the `ui://components/<name>@<version>` URI grammar

Keep the same `ui://` namespace your clients already expect; just add the `@version` suffix for trust-boundary resolution.

#### Keep your Streamable HTTP transport

GenicUI speaks Streamable HTTP at `/mcp`. Bearer auth stays the same.
::

**Effort:** Small — typically a 1–2 day spike to swap the resource layer. Reference app: `examples/migration-from-mcp-apps/` (planned — see [Verification](#verification)).

## From OpenAI Apps SDK

OpenAI Apps SDK uses the `_meta['openai/outputTemplate']` envelope to point at HTML templates hosted alongside the MCP server. GenicUI ships a runtime adapter that interprets the same `_meta` keys, so OpenAI consumers keep working unchanged while MCP-native consumers get the full registry.

### Wire-level diff

::tabs
:::tabs-item{icon="i-lucide-x" label="OpenAI Apps SDK"}
```json
// Tool call with UI hint
{
  "name":"show_dashboard",
  "_meta":{
    "openai/outputTemplate":"ui://templates/dashboard.html",
    "openai/widgetAccessible":true
  }
}
```

// Server returns inline HTML via resource
{"result":{"content":[{"type":"text/html","text":"<div>...</div>"}]}}
:::

:::tabs-item{icon="i-lucide-check" label="GenicUI"}
```json
// Same tool call — _meta is preserved
{
  "name":"show_dashboard",
  "_meta":{
    "openai/outputTemplate":"ui://components/dashboard@1.0.0",
    "openai/widgetAccessible":true
  }
}

// GenicUI resolves the URI to a registry entry and renders via render_component
{"result":{"componentId":"dash-..."}}
```
:::
::

### Migration steps

::steps{level="3"}
#### Move HTML templates into a GenicUI registry

Each `ui://templates/<name>.html` becomes a component entry in a registry package. The component's render function wraps your existing UI library — no template rewrite needed.

#### Keep the `_meta['openai/...']` envelope untouched

GenicUI's runtime reads it as a hint to apply OpenAI compatibility. OpenAI-side consumers see no change.

#### Add a GenicUI registry entry per template

```ts
const Dashboard = {
  name: 'dashboard',
  version: '1.0.0',
  uri: 'ui://components/dashboard@1.0.0',
  propsSchema: DashboardProps,
  framework: 'openai-template@1',
  tags: ['dashboard', 'analytics'],
  events: [],
  examples: [{ /* default empty state */ }],
};
```

#### Test with both OpenAI consumers and the GenicUI playground

The playground renders every registry entry; OpenAI-side consumers continue to receive `_meta`-shaped responses.
::

**Effort:** Medium — typically 3–5 days for a small template library. The `_meta` envelope preservation is what makes the migration reversible — you can dual-serve during the transition. Reference app: `examples/migration-from-openai/` (planned).

## From CopilotKit

CopilotKit is the AG-UI-native React framework. The wire is already compatible; what changes is the **surface**: React custom renderers become GenicElement + closed Shadow DOM Web Components.

### Wire-level diff

The wire is **identical**. CopilotKit emits AG-UI events; GenicUI consumes them. What changes is the *renderer*:

::tabs
:::tabs-item{icon="i-lucide-x" label="CopilotKit (React)"}
```tsx
// A CopilotKit custom renderer
const DataTable: React.FC<{rows: Row[]; columns: Column[]}> = ({ rows, columns }) => (
  <table className="copilotkit-table">
    <thead>{columns.map(c => <th key={c.key}>{c.label}</th>)}</thead>
    <tbody>{rows.map(r => <tr>{columns.map(c => <td>{r[c.key]}</td>)}</tr>)}</tbody>
  </table>
);
```

// State changes dispatched manually
useCopilotAction({ name: 'row_click', handler: ({ rowId }) => emit({ type: 'ROW_CLICKED', rowId }) });
```

:::tabs-item{icon="i-lucide-check" label="GenicUI (Web Component)"}
```ts
// A GenicElement subclass — closed Shadow DOM
class GenicDataTable extends GenicElement {
  static get observedAttributes() { return ['props']; }

  connectedCallback() {
    const { rows, columns } = this.props;
    const shadow = this.attachShadow({ mode: 'closed' });
    shadow.innerHTML = renderTable(rows, columns);
    this.addEventListener('click', (e) => {
      const rowId = (e.target as HTMLElement).dataset.rowId;
      this.dispatchEvent(new CustomEvent('row_click', {
        detail: { rowId },
        bubbles: true,
        composed: true, // crosses the closed Shadow DOM
      }));
    });
  }
}
customElements.define('genic-data-table', GenicDataTable);
```
:::
::

### Migration steps

::steps{level="3"}
#### Port each React renderer to a `GenicElement` subclass

The `props` attribute replaces `useProps()`; `dispatchEvent` replaces `useCopilotAction()`. Most custom renderers port in a 1:1 mapping.

#### Replace the React render tree with `<genic-*>` custom elements

Where the React tree had `<DataTable rows={...} />`, the GenicUI tree has `<genic-data-table props='{"rows":[...]}' />`.

#### Drop the React wrapper around the agent

GenicUI runs as a standalone Web Component — no React context provider needed. The agent's runtime (CopilotKit, LangGraph, plain AG-UI) consumes the same wire.

#### Re-test with the conformance runner

Each ported component needs to pass `@genicui/conformance` — closed Shadow DOM, `composed: true` events, and the 5-rule smoke.
::

**Effort:** Medium — typically a week per surface area. The biggest win is removing the React dependency from the runtime; the biggest cost is the learning curve on Web Component lifecycle. Reference app: `examples/migration-from-copilotkit/` (planned).

## Decision matrix — when to migrate

| Symptom | Migrate? | Path |
|---|---|---|
| **Web Components needed** (micro-frontends, embed in non-React apps) | ✅ Yes | Any |
| **Multiple UI surfaces** (chat + dashboard + command palette) sharing state | ✅ Yes | CopilotKit or MCP Apps |
| **Strict trust boundaries** (security review, sandboxed agents) | ✅ Yes | MCP Apps or fresh start |
| **One-off UI, single agent, no MCP server yet** | ❌ Hold | Stay on OpenAI Apps SDK until you need a second consumer |
| **React-only team, no Web Component experience** | ⚠️ Pilot first | Try CopilotKit migration on one surface before committing |
| **OpenAI-only distribution** | ⚠️ Optional | The `_meta` adapter runs GenicUI alongside OpenAI; no need to migrate |

::callout{type="tip"}
**Migrate surface by surface, not all at once.** The `_meta` adapter and the AG-UI wire compatibility mean GenicUI can run *alongside* your existing stack. Pick the lowest-friction surface (typically one component) and prove the round-trip before expanding.
::

## Verification

Each path's **observable outcome** is a working reference app under `examples/`. These are planned and tracked in the migration roadmap:

- `examples/migration-from-mcp-apps/` — replaces a `resources/list` consumer with `find_ui_component` + `render_component`.
- `examples/migration-from-openai/` — dual-serves an existing OpenAI Apps SDK server via GenicUI's `_meta` adapter.
- `examples/migration-from-copilotkit/` — ports a CopilotKit React renderer to a `GenicElement` Web Component.

::callout{type="warning"}
**Reference apps are not yet shipped.** The M5.1-T7 task scope covers the *guide*; the reference apps themselves are scoped for a follow-up milestone (see the [roadmap](/community/roadmap)). Until then, the migration steps above are the source of truth and the conformance suite is the only formal verification gate.
::
