This guide is the **how we verify** companion to the [testing strategy spec](/guides/testing#the-pyramid). It maps the 150/20/3-5 pyramid onto concrete `bun test` commands, walks the four required `fast-check` property tests, and explains the `@genicui/conformance` runner that every registry must pass before publishing.

## The pyramid

GenicUI follows the classic test pyramid — fast, isolated unit tests form the base; integration tests verify cross-package wiring; a thin e2e layer proves the whole loop in a real browser. Property tests sit beside the unit layer; the conformance suite is the registry-specific spike.

```
              ╱╲
             ╱  ╲         E2E smoke (3–5 tests)
            ╱    ╲        Full agent turn: render → update → event
           ╱──────╲
          ╱        ╲       Integration tests (~20)
         ╱          ╲      WebSocket frames, MCP tool calls, schema validation
        ╱────────────╲
       ╱              ╲    Unit tests (~150)
      ╱                ╲   SequenceGenerator, JsonPatchEngine, genicSchema, ...
     ╱──────────────────╲
```

| Layer | Count | Speed | Runs on |
|---|---|---|---|
| Unit | ~150 | <5s total | Every PR, pre-commit |
| Integration | ~20 | <30s total | Every PR |
| E2E smoke | 3–5 | <2min total | Pre-deploy, nightly |
| Conformance | N×3 (registry × versions) | <60s | Pre-publish |

::callout{type="info"}
**Why a thin e2e layer?** Unit and integration cover ~93% of bugs. E2E tests are slow and flaky — keep them focused on the *happy path that proves the wiring* and let the lower layers prove the contracts.
::

## Coverage targets

The lock-in from the [maintainability requirements](/guides/testing#coverage-targets):

| Component | Line | Branch |
|---|---|---|
| `@genicui/core` | 80% | 75% |
| `@genicui/server` | 80% | 75% |
| `@genicui/client` | 70% | 65% |
| Tool handlers | **90%** | 85% |
| Registry adapters | 60% | 55% |
| Framework shims | 60% | 55% |

**Enforcement:** `bun test --coverage` in CI fails the build if any component drops below target. Tool handlers carry the highest target because they are the trust-boundary surface — every tool call passes through them.

## Layer 1 — Unit tests

Pure logic, no I/O. Located next to source as `*.test.ts`.

```bash
bun test packages/*/src
```

Example — `packages/core/src/patch/engine.test.ts`:

```ts
import { describe, it, expect } from 'bun:test';
import fc from 'fast-check';
import { JsonPatchEngine } from './engine';

describe('JsonPatchEngine', () => {
  it('round-trips random pairs (property test)', () => {
    fc.assert(
      fc.property(
        fc.object({ maxDepth: 3 }),
        fc.object({ maxDepth: 3 }),
        (a, b) => {
          const engine = new JsonPatchEngine();
          const patch = engine.diff(a, b);
          return JSON.stringify(engine.apply(patch, a)) === JSON.stringify(b);
        }
      ),
      { numRuns: 10_000 },
    );
  });

  it('returns empty patch for identical objects', () => {
    const engine = new JsonPatchEngine();
    expect(engine.diff({ a: 1 }, { a: 1 })).toEqual([]);
  });
});
```

## Layer 2 — Integration tests

Server + client + transport together. Located in `tests/integration/`. An in-process WS server makes these run in <30s total.

```bash
bun test tests/integration
```

Example — `tests/integration/render-update.test.ts`:

```ts
import { test, expect } from 'bun:test';
import { startTestServer } from '../helpers/server';
import { connectTestClient } from '../helpers/client';

test('agent renders and updates a DataTable', async () => {
  const { server, port } = await startTestServer({ apiKey: 'gnc_live_test' });
  const client = await connectTestClient(`ws://localhost:${port}/ws`, 'gnc_live_test');

  // Render
  const mounted = await client.call('render_component', {
    name: 'data-table',
    props: { rows: [{ id: '1', name: 'Alice' }], columns: [{ key: 'name', label: 'Name' }] },
    surface: 'default',
  });
  expect(mounted.componentId).toMatch(/^dt-[a-f0-9]{8}-[0-9A-HJKMNP-TV-Z]{26}$/);

  // Wait for COMPONENT_MOUNTED
  const mountedFrame = await client.nextFrame(mounted.componentId);
  expect(mountedFrame.type).toBe('COMPONENT_MOUNTED');

  // Update
  await client.call('update_component', {
    componentId: mounted.componentId,
    patch: [{ op: 'replace', path: '/rows/0/name', value: 'Alicia' }],
  });

  // Verify STATE_DELTA arrives
  const delta = await client.nextFrame(mounted.componentId);
  expect(delta.type).toBe('STATE_DELTA');
  expect(delta.payload).toEqual([{ op: 'replace', path: '/rows/0/name', value: 'Alicia' }]);

  await server.close();
});
```

## Layer 3 — End-to-end smoke

Real browser + real agent. Playwright drives the browser; an MCP inspector drives the agent. Reserved for the full `render → update → event` loop.

```bash
bunx playwright test e2e/full-flow.spec.ts
```

::callout{type="warning"}
**E2E runs pre-deploy, not on every PR.** The full Playwright suite takes ~2min; budget it for the deploy pipeline and nightly runs, not the inner loop.
::

## Property tests

For invariants where enumerating cases is impossible, use `fast-check`. GenicUI requires five property tests, each running 10K random cases:

| Feature | Property |
|---|---|
| F3 `SequenceGenerator` | 10K `seq.next()` calls produce monotonic uint64, no duplicates |
| F4 `JsonPatchEngine` | 10K random object pairs satisfy `apply(diff(a, b), a) === b` |
| F2 `GenicSchema` | All TypeBox types round-trip to JSON Schema 2020-12 + back without loss |
| F14 Trust boundary | 10K random payloads with `__proto__`, `constructor`, `prototype` all strip those keys |
| F21 Error codes | 10K random tool calls return codes in `[-32010, -32001]` or the standard MCP range |

Run them explicitly when iterating on the trust boundary:

```bash
bun test --pattern 'property'
```

## Conformance suite

`@genicui/conformance` is the cross-registry contract — every registry PR must pass before merge.

```ts
// in @genicul-primevue/registry package
import { runConformance } from '@genicui/conformance';
import { registry } from './dist/registry.js';

await runConformance(registry, {
  framework: 'vue3',
  mountPoint: '#test-root',
});
```

The five conformance rules:

1. **Schema valid** — every `propsSchema` parses with `genicSchema()`.
2. **Events declared** — every `composed: true` event has a `detailSchema`.
3. **Lifecycle clean** — `connectedCallback` → render, `disconnectedCallback` → cleanup.
4. **State queries work** — `getState()` returns the same shape as `initialState`.
5. **Wire integration** — render → update → event flow works in a smoke test.

Registry PRs that fail conformance are auto-blocked by `.github/workflows/registry-conformance.yml`.

## Authoring rules

The 6 rules from the testing strategy, restated for grep-ability:

1. **ACs map 1-to-1 to tests.** Each `Given/When/Then` AC gets a test named `<FEATURE>-AC<n>`.
2. **Red-green-refactor.** AC first, failing test second, implementation third.
3. **No network in unit tests.** Stubs for WebSocket, fetch, etc. If you need a network, it belongs in integration or e2e.
4. **Deterministic tests.** All randomness comes from `fast-check`. No `Math.random()`, no `Date.now()` in test bodies — pass timestamps as fixtures.
5. **One assertion per `it()`.** Use `expect()` chains sparingly. If a test has 5+ assertions, split it.
6. **Real references where possible.** Bun's in-process WebSocket is fast enough that mocking is rarely worth the loss of confidence.

## Per-tool test pattern

For each MCP tool, the canonical test layout lives in `packages/server/src/mcp/__tests__/`. The pattern is **one file per tool, four test groups**:

```
render_component.test.ts
├── AC1: returns valid componentId for valid props
├── AC2: rejects unknown component name (-32004)
├── AC3: rejects payload with __proto__/constructor/prototype (-32003)
└── AC4: emits COMPONENT_MOUNTED on the component's channel
```

The same shape applies to `find_ui_component`, `update_component`, and `subscribe_to_events`. Use `bun test packages/server/src/mcp/__tests__/` to run the full MCP surface.

## CI matrix

| Job | Tooling | Time budget |
|---|---|---|
| Lint + format | ESLint, Prettier | 30s |
| Typecheck | `tsc --noEmit` | 60s |
| Unit + integration | `bun test` | 60s |
| Coverage gate | `bun test --coverage` | 90s |
| Property tests | `bun test --pattern property` | 120s |
| Build | `bun run build` | 60s |
| E2E smoke (PR only) | Playwright | 180s |
| Conformance (registry PR) | `bun run test:conformance` | 60s |

Total PR CI: ~7 minutes. **Stated budget** — PRs that exceed it get a `perf-budget-exceeded` label.

## Verification

A passing PR needs four observable signals:

```bash
bun test --coverage          # exits 0, all targets met (80/90/60)
bun test --pattern property  # exits 0, 5 property suites green
bun run build                # exits 0
bun run lint                 # exits 0
```

If any one fails, the PR is blocked. Coverage regressions are the most common culprit — bump the target only with an explicit `coverage-justified` label and an updated baseline.
