GenicUI is an **MCP-native, generative agentic UI framework** rendered as Web Components. It lets any AI agent — Claude Code, GPT, Cursor, or your own — render, update, and respond to real UI components in your existing application.

You keep your component library (PrimeVue, Mantine, shadcn, Skeleton, anything). GenicUI wraps it with a thin adapter, declares each component's contract in one place, and exposes the catalog through four standard MCP tools.

## Why GenicUI?

Most AI-agent UI integrations fall into one of three traps. GenicUI avoids all of them.

### MCP-native, not framework-only

GenicUI speaks the [Model Context Protocol](https://modelcontextprotocol.io/) directly. Any MCP-capable agent discovers your components via `find_ui_component`, mounts them via `render_component`, updates them via `update_component`, and subscribes to user interactions via `subscribe_to_events`. There is no proprietary SDK for the agent to install.

::callout{type="info"}
The four MCP tools are the entire wire protocol. If your agent supports MCP, it supports GenicUI.
::

### Web Components, not iframes

Components render as native `<genic-element>` custom elements inside your application's DOM tree. They inherit your CSS variables, your theme, your layout system, and your accessibility context. No sandboxed iframe. No postMessage plumbing. No styling collisions.

### JSON-Patch wire, not full re-render

When the agent updates a component, GenicUI ships a [RFC 6902 JSON-Patch](https://datatracker.ietf.org/doc/html/rfc6902) over the wire — only the changed properties traverse the network. The browser applies the patch to the live component instance. Render cost stays O(diff) instead of O(component).

## How it fits

```text
┌──────────┐    MCP tools     ┌──────────────┐   WebSocket   ┌──────────────┐
│  Agent   │ ───────────────► │ GenicUI      │ ─────────────►│   Browser    │
│ (Claude) │   JSON-RPC POST  │ server       │  JSON-Patch   │  <genic-     │
│  Code)   │ ◄─────────────── │ (port 3040)  │ ◄───────────── │   element>   │
└──────────┘                  └──────────────┘               └──────────────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │   Registry   │
                              │  (catalog +  │
                              │  schemas)    │
                              └──────────────┘
```

1. **Agent** discovers the `DataTable` component by calling `find_ui_component({ tag: "table" })`.
2. **Server** resolves the catalog entry, validates props against the TypeBox schema, and mounts the component.
3. **Browser** receives the mount frame over WebSocket and renders `<genic-element>` inside your app.
4. **User** clicks a row → the event is forwarded back to the server → the agent's next turn sees `row_selected` as a tool result.

## Who it's for

| Role | Use GenicUI for |
|---|---|
| **Agent developers** | Shipping a chat surface where the model calls real UI instead of returning JSON blobs. |
| **Framework shim consumers** | Wrapping PrimeVue / Mantine / shadcn so an external agent can drive them without a custom SDK. |
| **Registry authors** | Publishing a typed component catalog that any MCP-capable agent can consume. |
| **Operators** | Running GenicUI in a multi-tenant environment with per-tenant API keys and component allow-lists. |

## What you get

- **Five core packages** — `@genicui/core`, `@genicui/server`, `@genicui/client`, `@genicui/vite-plugin`, `@genicui/agent-bridge`.
- **One reference registry** — `@genicul-primevue/registry` with six production-ready components.
- **A live playground** — `examples/playground/` boots a Nuxt 4 app wired to a real GenicUI server.
- **A working Claude Code integration** — register the server via `claude mcp add` and start rendering components from chat.
