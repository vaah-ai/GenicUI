Replace the built-in API-key check with a JWT, OAuth, or mTLS validator. The GenicUI server exposes `wrapWithValidation()` for exactly this — insert your auth middleware ahead of the trust-boundary pipeline so a bad token never reaches `stripProtoKeys`.

## Problem

You need to authenticate agents against your existing identity provider (Auth0, Clerk, AWS Cognito, internal OAuth). The shipped API-key path (`X-API-Key: gnc_live_…`) is great for service-to-service but doesn't satisfy an enterprise customer's SAML/JWT requirement.

## Solution

Run your token validation in front of the server's tool handlers. The trust boundary (`stripProtoKeys` → `Value.Check`) only runs after your auth middleware returns 200; rejected tokens short-circuit with the standard `-32007 auth_invalid` JSON-RPC code.

::callout{type="info"}
The auth check runs in step **0** of the pipeline — see [Trust Boundary › The input validation pipeline](/concepts/trust-boundary#the-input-validation-pipeline). A failure here never reaches step 1, so you can't accidentally pollute the idempotency cache with an invalid payload.
::

## Code

```ts [packages/server/src/auth/jwt-middleware.ts]
import { jwtVerify, createRemoteJWKSet } from 'jose';
import type { Middleware } from './middleware.js'; // local middleware type

const JWKS = createRemoteJWKSet(new URL(process.env.JWT_JWKS_URL!));

export const jwtAuth: Middleware = async (req, next) => {
  const header = req.headers.get('authorization') ?? '';
  const token = header.replace(/^Bearer\s+/i, '');
  if (!token) {
    return Response.json({ error: 'missing_token' }, { status: 401 });
  }
  try {
    const { payload } = await jwtVerify(token, JWKS, {
      issuer: process.env.JWT_ISSUER,
      audience: 'genicui-server',
    });
    // Attach the verified subject so handlers can scope per-user state
    (req as any).auth = { sub: payload.sub, scope: payload.scope };
    return next(req);
  } catch (err) {
    return Response.json({ error: 'invalid_token' }, { status: 401 });
  }
};
```

Wire it into the server's middleware chain before `wrapWithValidation()`:

```ts [packages/server/src/index.ts]
import { jwtAuth } from './auth/jwt-middleware.js';

export function createServer(): Elysia {
  return new Elysia()
    .use(jwtAuth)                          // ← runs first
    .use(wrapWithValidation())             // ← trust boundary
    .mount('/mcp', mcpRouter)
    .mount('/ws', wsRouter);
}
```

## Verification

```bash
# 1. Boot the server with the JWKS URL set
JWT_JWKS_URL=https://your-idp.example.com/.well-known/jwks.json \
JWT_ISSUER=https://your-idp.example.com/ \
bun packages/server/bin/start.ts

# 2. Send an authenticated tool call with a valid JWT
TOKEN=$(your-idp-cli issue --aud genicui-server)
curl -X POST http://localhost:3040/mcp \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":"1","method":"tools/list"}'
# expect: 200 OK with the tool catalog

# 3. Send the same call with a bad token
curl -X POST http://localhost:3040/mcp \
  -H "Authorization: Bearer not.a.real.jwt" \
  -d '{"jsonrpc":"2.0","id":"1","method":"tools/list"}'
# expect: 401 with { "error": "invalid_token" }
```

A 401 on step 3 confirms the trust boundary never ran. If you see `-32003 props_invalid` after step 3, your middleware is wired *after* `wrapWithValidation()` — swap the order.

## Pitfalls

- **Don't trust the body.** Auth must read the `Authorization` header only. A request body containing `"apiKey": "gnc_live_…"` is just data — `wrapWithValidation()` would otherwise process it as props.
- **Cache the JWKS.** `createRemoteJWKSet()` already does this, but if you write your own key resolver, cache the keyset with a 10-minute TTL — hammering your IdP on every request is a denial-of-service vector against yourself.
- **Set `clockTolerance` to 30s.** Clock drift between the agent host and the IdP is the #1 cause of spurious `-32007 auth_invalid` errors. `jose` accepts `clockTolerance: 30` in the verify options.
- **Forward the scope.** If your IdP issues scopes (`payload.scope`), attach them to `req.auth` and reject at the tool layer with `-32007` when a token lacks the required scope. Don't bake scope checks into the middleware — they belong next to the tool definition.
- **Never log the token.** F46 ships a log scrubber that redacts known patterns; your custom middleware must add the token prefix (`Bearer ` + first 8 chars) to the scrub list. Otherwise a `console.log(req.headers)` will leak credentials.
