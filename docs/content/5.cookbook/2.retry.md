Your agent's `render_component` call timed out. Was it mounted or not? Without idempotency, a retry double-mounts; with it, the second call returns the same `componentId` from the server's 24h LRU cache. This recipe shows the client-side retry loop that survives network flakes without producing duplicate components.

## Problem

Agents retry on every transient failure — Claude Code's MCP wrapper retries on timeouts and 5xx responses by default. A naive retry of `render_component` allocates a fresh `componentId` and renders the component twice. The user sees a flash of the old UI, then the new one replaces it.

## Solution

Two layers of defense:

1. **Idempotency key** (`idempotencyKey` / `clientRequestId`) — the server caches the response for 24h keyed by `(apiKey, idempotencyKey)`. A retry with the same key returns the original response.
2. **Exponential backoff with jitter** — the client waits 1s, 2s, 4s, 8s (capped at 30s) with ±25% jitter between attempts. After 5 attempts, dead-letter the call.

::callout{type="info"}
The 24h TTL is enforced by an LRU cache. See [Frames › Idempotency keys](/concepts/frames#idempotency-keys) for the cache key shape and the silent-eviction policy.
::

## Code

```ts [lib/retry.ts]
import { randomUUID } from 'node:crypto';

type RetryOpts = {
  maxAttempts?: number;     // default 5
  baseMs?: number;          // default 1_000
  capMs?: number;           // default 30_000
  jitter?: number;          // default 0.25 (±25%)
};

const TRANSIENT = new Set([408, 425, 429, 500, 502, 503, 504, 1013]);

export async function withRetry<T>(
  fn: (key: string) => Promise<T>,
  opts: RetryOpts = {},
): Promise<T> {
  const { maxAttempts = 5, baseMs = 1_000, capMs = 30_000, jitter = 0.25 } = opts;
  // Stable per-call-site key — reused across retries
  const idempotencyKey = randomUUID();
  let lastErr: unknown;
  for (let attempt = 1; attempt <= maxAttempts; attempt++) {
    try {
      return await fn(idempotencyKey);
    } catch (err: any) {
      lastErr = err;
      const status = err?.status ?? err?.code;
      const retryable = TRANSIENT.has(status) || err?.name === 'AbortError';
      if (!retryable || attempt === maxAttempts) throw err;
      const backoff = Math.min(baseMs * 2 ** (attempt - 1), capMs);
      const wait = backoff * (1 + (Math.random() * 2 - 1) * jitter);
      await new Promise((r) => setTimeout(r, wait));
    }
  }
  throw lastErr;
}
```

Use it for every tool call that mutates state:

```ts [lib/render.ts]
import { withRetry } from './retry.js';
import { callTool } from './mcp-client.js';

export const renderDataTable = (props: Record<string, unknown>) =>
  withRetry((key) =>
    callTool('render_component', {
      name: 'DataTable',
      props,
      idempotencyKey: key,   // ← same key on every retry
    }),
  );
```

## Verification

Send 5 identical requests with the same `idempotencyKey` and confirm the server mounts exactly once:

```bash
KEY=$(uuidgen)
for i in 1 2 3 4 5; do
  curl -s -X POST http://localhost:3040/mcp \
    -H "Authorization: Bearer $GENICUI_API_KEY" \
    -H "Content-Type: application/json" \
    -d "{\"jsonrpc\":\"2.0\",\"id\":\"$i\",\"method\":\"tools/call\",\"params\":{\"name\":\"render_component\",\"arguments\":{\"name\":\"DataTable\",\"props\":{\"rows\":[]},\"idempotencyKey\":\"$KEY\"}}}"
done

# All five responses should share the same componentId, e.g.:
# {"componentId":"dt-sess9f8e-01HK9X"}
```

The server log will show exactly one `STATE_SNAPSHOT` and one `COMPONENT_MOUNTED` emission. If you see five mounts, your retry layer is generating a fresh key per attempt — check `withRetry`.

## Pitfalls

- **Don't reuse keys across `render` vs `update`.** A `render_component` key and a later `update_component` call sharing the same key collide — the server sees a `params` mismatch and returns `-32007 idempotency_conflict`. Use the same key *only* across retries of the same logical operation.
- **Keys expire after 24h.** A user who retries a render that succeeded yesterday gets a fresh mount and a second `componentId`. Persist `(componentId, idempotencyKey)` pairs in your session store if you need to survive TTL eviction.
- **Backoff cap of 30s matches the server.** The runtime's reconnect loop also uses 30s as its cap ([Events › Backpressure](/concepts/events#backpressure-and-rate-limits)). Capping client-side backoff higher just makes you look hung to the user.
- **Dead-letter, don't silently drop.** After `maxAttempts`, persist the failed call to a queue (Redis Streams, SQS, a local SQLite). Surface it in your agent's UI as "1 retryable failure, click to retry" — silent drops are how users lose trust.
- **Don't retry `-32003 props_invalid`.** Validation errors are deterministic — retrying won't fix them. Add `400` to the non-retryable list (it's not in `TRANSIENT` above) and surface the error to the user.
- **Skip the retry for `401`/`403`.** Token expiry needs a refresh, not a backoff. Catch `err.status === 401` separately, refresh the token, then retry *once* with the new bearer.
