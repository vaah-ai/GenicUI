You depend on `@genicul-primevue/registry` but want to ship your own `DataTable` with custom props (e.g., a `csvExport` action your product team needs). Two registries now declare `DataTable`. Which wins?

## Problem

You ship an internal `@acme/data-table@2.0.0` to a customer who already has the official `@genicul-primevue/registry@1.0.0` installed. Both export a `DataTable` component. The agent's `find_ui_component` returns one; the other is invisible. Worse, the agent silently picks the "wrong" one and the customer's UI breaks.

## Solution

GenicUI loads registries from three tiers — **Project > User > Remote** — and the higher tier always wins. To force a specific version, pin it explicitly in your `registry.json` with a `version` constraint; the loader applies the pin *before* tier resolution, so a pin beats tier.

::callout{type="info"}
The default remote allow-list is `@genicul-primevue/registry` only. Other remote entries are dropped with a log warning. See [Registries › Trust tiers and resolution order](/concepts/registries#trust-tiers-and-resolution-order).
::

## Code

Pin a specific version in your project-level `registry.json`:

```json [registry.json — project tier]
{
  "id": "@acme/data-table",
  "version": "2.0.0",
  "trustTier": "project",
  "components": ["DataTable"],
  "pin": {
    "DataTable": {
      "registry": "@acme/data-table",
      "version": "2.0.0",
      "reason": "Internal-only DataTable with csvExport action."
    }
  }
}
```

Install both registries and let the loader resolve the conflict:

```bash
bun add @genicul-primevue/registry    # official, remote tier
bun add @acme/data-table              # internal, project tier
```

On boot, the loader walks each tier in order and applies your `pin`:

```text
[bootstrap] Loading registry "@acme/data-table@2.0.0" (project) — 1 component
[bootstrap] Loading registry "@genicul-primevue/registry@1.0.0" (remote) — 5 components
[bootstrap] Conflict on DataTable:
            project @acme/data-table@2.0.0   (pinned) ← winner
            remote  @genicul-primevue@1.0.0  (shadowed)
[bootstrap] Effective registry: 5 components (4 PrimeVue + 1 internal)
[bootstrap] WARNING: PrimeVue DataTable shadowed by pin. Set GENICUI_REGISTRY_DRY_RUN=1 to verify the pin before promoting.
```

To run the loader in dry-run mode and see the resolution *without* committing:

```bash
GENICUI_REGISTRY_DRY_RUN=1 bun packages/server/bin/start.ts
# The server prints the resolution matrix and exits without binding the port.
```

For coexisting registries where you want *both* available (different component names, no conflict), no pin is needed:

```text
@genicul-primevue/registry@1.0.0   → DataTable, InputPair, ResultCard, CityPicker, WeatherCard
@acme/charts@1.0.0                 → AreaChart, BarChart, PieChart
                                ─────
Effective registry                → 8 components (5 + 3, zero overlap)
```

## Verification

```bash
# 1. Install the conflicting pair
bun add @genicul-primevue/registry
bun add @acme/data-table

# 2. Dry-run the loader to verify resolution
GENICUI_REGISTRY_DRY_RUN=1 bun packages/server/bin/start.ts
# expect: PrimeVue DataTable shadowed, @acme/data-table@2.0.0 wins

# 3. Confirm via find_ui_component — only the pinned entry shows
curl -X POST http://localhost:3040/mcp \
  -H "Authorization: Bearer $GENICUI_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":"1","method":"tools/call","params":{"name":"find_ui_component","arguments":{"query":"DataTable","topK":3}}}'
# expect: result lists ONLY @acme/data-table@2.0.0, no PrimeVue entry

# 4. Render and verify the schema matches the pinned component
curl -X POST http://localhost:3040/mcp \
  -H "Authorization: Bearer $GENICUI_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":"2","method":"tools/call","params":{"name":"render_component","arguments":{"name":"DataTable","props":{"rows":[],"csvExport":true}}}}'
# expect: 200 OK; schema returned includes the csvExport prop
```

A schema-rejection on step 4 means the pin didn't take effect — your `registry.json` is in the wrong directory (project tier expects `./registry.json` at the workspace root) or the JSON is malformed.

## Pitfalls

- **Trust tier is silent.** No toast, no banner — the loader just resolves and moves on. If you shadow a third-party component by accident, the agent picks the wrong one with zero diagnostic. Always `GENICUI_REGISTRY_DRY_RUN=1` before promoting to production.
- **Pins are absolute.** A pinned component can't be temporarily overridden for one user or session. If you need per-tenant customization, build a *different* registry (e.g., `@acme/data-table-tenant-a`) and let the agent pick via `find_ui_component`'s `tags` filter — don't rely on tier resolution for per-user variations.
- **Bump the major on breaking schema changes.** The trust boundary rejects registries that change a `propsSchema`'s required keys without a major bump. See [Building a Custom Registry](/guides/custom-registry#publishing) — semver matters here because the schema check is strict.
- **Don't pin to `latest`.** A floating pin becomes a silent source of nondeterminism — your dev environment picks up the latest release, your staging picks up a different one. Always pin to an exact version (`2.0.0`, not `^2.0.0`).
- **Hot reload on `SIGHUP` only updates unpinned components.** A pinned entry is read once at boot; sending `SIGHUP` won't re-resolve the pin. Restart the server to pick up a new pinned version.
- **Two registries, one URI, different schemas** — never allow this in production. The loader throws at boot if the same `ui://` URI is claimed by two registries in the same tier. Move one to a different URI namespace (`ui://acme/...` vs `ui://genicul/...`).
